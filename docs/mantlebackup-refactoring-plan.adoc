= mantlebackup_controller.go 段階的リファクタリング計画

== 目的

link:new-architecture.adoc[Mantle（再）設計案]に従い、`internal/controller/mantlebackup_controller.go`（約 3,900 行、以下 MB-C）を三層アーキテクチャ（ドメイン層・ユースケース層・インフラ層）にリファクタリングする。このリファクタリングにより以下を達成する：

* 本体コードの関心を分離し、Kubernetes クラスタや Ceph クラスタといった外部リソースにアクセスする部分（インフラ層）と、コントローラが次に何を行うべきかを判定する部分（ドメイン層）を分けることで、コードの見通しをよくする。ドメイン層では、どのような状況でリコンサイラがどのように振る舞うのかを明示的に書く。
* ドメイン層に対して Arrange-Act-Assert を明示した（envtest を用いない）ユニットテストを書き、リコンサイラの振る舞いを担保する。
* 実装中は https://martinfowler.com/bliki/StranglerFigApplication.html[ストラングラーフィグパターン]を活用し、レビューしやすい単位に PR を分割して進める。各 PR は単体でマージしても外部から見た振る舞いや機能を損ねず、コンパイルが通る。その代わり、PR 単体では nop になるコード（後続 PR から使われるコード）を許容する。

MantleBackupConfig コントローラで実施済みの PoC（ https://github.com/cybozu-go/mantle/pull/244[PR #244] 他。`internal/controller/domain`・`usecase`・`infra` パッケージ）のパターンを正とし、同じディレクトリ・同じ流儀で実装する。

== 計画と実装の差異

PR 1〜3 の実装は、本書の当初の記述と次の点で異なる。後続 PR に影響するものは各 PR の記述にも反映済み。

[#diff-pr3-policy]
=== PR 3 の方針変更

実装の過程で、PR 2・PR 3 の方針を次のように変更した（この決定に従い、両者は 1 つの PR としてマージされた）：

* **スケルトンは `Provision`・`Finalize` を呼び出すコードパスを作ることだけを目的とし、それ以外のものは含めない。** したがって PR 3 で予定していたリコンサイル対象 `MantleBackup` の永続化（`DeepCopy`・dirty 判定・`Update`/`Status().Update`・resourceVersion の引き継ぎ・競合時の方針）と Operations の引き渡し機構は、この PR では導入しない。
* **永続化・Operations の機構は、後続 PR で必要になった時点で導入する。**
* **この規模ではユニットテストは不要と判断した。**

この決定により、<<migration-strategy-note,移行戦略>>の方針 4（使用するコンポーネントを移す PR で一緒に導入する）が、`Run` の永続化機構と Operations 引き渡し機構そのものにも適用される。導入先は次の通り：

* Operations の引き渡し機構・ドメイン層の `ReconcilerOperations` フィールド・MB 用 Operation 型・インフラ層の実行器・打ち切り契約 → **PR 5**（`DeleteMantleBackupOperation`・`ScheduleExpireOperation` を初めて使う PR）。
* `Run` の永続化機構 → **PR 6**（ラベル・finalizer・status を初めて書き込む PR）。PR 4・PR 5 のドメイン処理はリコンサイル対象を変更しないため、それまで永続化は不要。
* 対応する AAA ユニットテストも、それぞれ PR 5・PR 6 で追加する。PR 4 以降は各 PR で必ずユニットテストを追加する。

=== その他の差異

legacy 委譲シグナルの置き場所::
本書は PR 3 で「ドメイン層に定義する一時的な戻り値」として導入するとしていたが、実装は `internal/controller/internal/reconcile` の `Result` に `legacy` フィールドと `ContinueWithLegacyReconcile()`・`ShouldContinueWithLegacyReconcile()` を追加する形になっている。PR 16 での撤去対象もこの位置になる。

`ShouldReturn()` が legacy を見ない::
`Result.ShouldReturn()` は `finished`・`requeueing`・`slowRequeueing`・`err` だけを見るため、legacy 委譲シグナルは「継続」として扱われる。`ToCtrlResult()` に渡すと「完了・エラーなし」と同じゼロ値になり、リコンサイルがサイレントに打ち切られる（`reconcile.go` の doc コメントも `ToCtrlResult` より前に確認することを要求している）。**`Run` の中に `*reconcile.Result` を返す下請けヘルパを追加する際は、`if result.ShouldReturn() { return result }` だけでは legacy を取りこぼす**ことに注意する（<<risk-legacy>> 参照）。

ユースケース層の初期化に `sync.Once` を使っていない::
実装は `NewMantleBackupReconciler` の中でインフラ層の Kubernetes クライアントと 3 ロール分のユースケース層コンポーネントを即時初期化している。<<d5>> の記述をこれに合わせて修正済み。

`checkManagedBackup` が `Reconcile` に残っている::
実装の `Reconcile` は「`Get` → `checkManagedBackup` → `usecase.Run` → legacy 委譲の分岐」の順で処理する。<<managed-backup-preflight,管理対象の事前判定>>をユースケース層へ移すのは PR 5 の作業であり、その際に `Reconcile` 側の呼び出しを削除する。

1 回のリコンサイルで `MantleBackup` を 2 回取得している::
`Reconcile` が取得した `backup` を渡さず、`usecase.Run` には `req.NamespacedName` だけを渡して `Run` が改めて取得する。旧コード経路は `Reconcile` が取得した方を使う。現時点では無害だが、**PR 6 で `Run` が永続化を行うようになると、legacy 委譲でフォールバックした旧コードが古い `backup` を触る**恐れがある（<<risk-legacy>> 参照）。

ロール分岐の `switch` が 2 段ある::
新経路（`usecase.Run` の呼び分け）と旧コード経路（`reconcileAs*` の呼び分け）で `switch r.role` が重複している。PR 9・13・16 でロールごとに旧コード側の case を畳んでいく。

MB 用のユニットテストがまだ 1 件も無い::
`domain`・`usecase` パッケージのテストは MBC PoC のもの（`domain/mbc_primary_reconciler_test.go`・`usecase/reconcile_mbc_primary_test.go`）だけである。

ドメインリコンサイラが `ReconcilerOperations` を持たない::
実装の `MB{Standalone,Primary,Secondary}Reconciler` は空の構造体で、`Provision`・`Finalize` の引数もリコンサイル対象の `MantleBackup` だけである（MBC PoC の `MBCPrimaryReconciler` は `Operations` フィールドを持つ）。PR 5 で Operations を導入する際に追加する。

== 現状の構造

`MantleBackupReconciler` は 3 つのロール（standalone / primary / secondary）で動作し、`Reconcile()` がロールごとの処理に分岐する。主なサブフローと外部アクセスは次の通り：

[cols="2,3,2", options="header"]
|===
| サブフロー | 主な関数 | 外部アクセス

| 管理対象判定
| `checkManagedBackup`
| K8s（PVC・StorageClass の読み取り）

| 期限切れ処理
| `expire`, `scheduleExpire`
| K8s（MantleBackup 削除）、`expireQueueCh` による遅延 requeue

| ローカルバックアップ

| レプリケーション（primary）

補足事項：

* 全サブフローは `internal/controller/internal/reconcile` パッケージの `*reconcile.Result`（succeeded / requeue / slow requeue / error の四値と、移行期間中の legacy 委譲シグナル）を、単独または多値返却の一部（`getSnapshotTarget`・`checkJobStatus`・`lockVolume` など）として返す（workqueue に登録するハンドラ関数である `scheduleExpire` を除く）。slow requeue は `SLOW_REQUEUE_RECONCILIATION_AFTER` 由来の長い遅延を持ち、優先度待ちで使われる。legacy 委譲シグナルは `ShouldReturn()` の対象外である（<<plan-impl-diff>> 参照）。
* MB-C の先頭で定義されているラベル・アノテーション・sync-mode などの定数は、スコープ外の `replication.go` からも参照されている（primary↔secondary 間のワイヤ契約）。さらに `LabelBackupPriority`・`MantleBackupConfigUID` は `cmd/backup`（MantleBackup を作成する Job）からも参照されており、`MantleBackupConfigUID` は `cmd/backup/main.go` に同じ文字列の定義が重複している。定数をドメイン層へ移す PR ではこれらの参照者も考慮する。
* `Make*Name`・`ExtractPartNumFrom*`・`searchForDiffOriginMantleBackup`・`calculateExportDataPVCSize`・`isHighPriority` などの純粋関数が多数存在し、これらは MB-C とテスト（E2E の `testutil` を含む）以外から参照されていない。`MakeObjectNameOfExportedData` は転送圧縮の導入により `(name, uid string, index int, transferCompression string)` を引数に取り、`zstd` 指定時はオブジェクト名に `.zst` を付ける。
* `exportedDiffSizeCache`（メトリクス用のメモリ内キャッシュ）と `expireQueueCh`（遅延 requeue 用チャネル）という 2 つの内部状態を持つ。このほか `objectStorageClient`（遅延初期化される S3 クライアント）も可変な内部状態である（<<d5>> 参照）。またスケルトン導入（PR 2・3）により `reconcileMB{Standalone,Primary,Secondary}` の 3 フィールド（ユースケース層コンポーネントへの参照）が加わっている。
* 転送圧縮（`spec.transferCompression`）は export/upload/import Job の spec（`TRANSFER_COMPRESSION` 環境変数）とオブジェクトストレージ上のオブジェクト名の双方に影響する（<<d4>> 参照）。
* export/upload/import Job の Pod には `PrimarySettings`・`SecondarySettings` 由来の affinity が設定される。zero-out Job と verify Job には設定されない。
* 優先度機能の導入により MB-C は MantleBackupConfig を読む（`mantlebackupconfigs` に対する `list;watch` の RBAC が追加されている）。

== 目標構造

リファクタリング完了後の構成は次の通り。

ドメイン層（`internal/controller/domain`）::
ロールごとのドメインリコンサイラを定義する：
+
* `MBStandaloneReconciler`
* `MBPrimaryReconciler`
* `MBSecondaryReconciler`
+
それぞれが `Provision`・`Finalize` メソッドを持ち、new-architecture.adoc の指示通り「`if 条件 { return 処理 }` の逐次実行」スタイルで記述する。standalone と primary が共有するローカルバックアップ処理は、ドメイン層内の共通関数（または両者に埋め込む共通構造体）として括り出す。リコンサイル対象の `MantleBackup` への変更はメモリ上で行い、それ以外の外部作用はドメインイベント（`domain.Operation`）として `ReconcilerOperations` に蓄積するか、ドメイン層で定義した narrow interface を介して行う（使い分けは <<d3>> 参照）。

ユースケース層（`internal/controller/usecase`）::
ロールごとに `ReconcileMBStandalone`・`ReconcileMBPrimary`・`ReconcileMBSecondary` を定義し、それぞれの `Run` が「リコンサイル対象と管理対象判定に必要なリソースの取得 → 管理対象の事前判定 → その他の必要リソースの取得 → `DeletionTimestamp` による `Provision`/`Finalize` の呼び分け → 変更された `MantleBackup` の永続化 → Operations のインフラ層への引き渡し」を行う。PoC の `ReconcileMBCPrimary.Run` と同じ流儀だが、管理対象外の backup に対してロール固有の外部アクセスを行わないための事前判定を追加する（<<managed-backup-preflight>>）。

インフラ層（`internal/controller/infra` ほか）::
`infra.KubernetesClient.ApplyReconcilerOperations` に MantleBackup 用の Operation の実行を追加する。Ceph 操作は既存の `ceph.CephCmd`（インターフェース＋gomock 生成済み）を、オブジェクトストレージ操作は既存の `objectstorage.Bucket`（インターフェース＋モックあり）を、gRPC 操作は `proto.MantleServiceClient` をそれぞれ実装として利用する。`mantlebackup_controller.go` は最終的に `SetupWithManager` と、ロールに応じてユースケース層の `Run` を呼ぶだけの薄い `Reconcile` のみになる。

== 主要な設計判断

[#d1]
=== D1: リコンサイル結果（requeue）の表現

ドメイン層の `Provision`・`Finalize` およびその下請け関数は、既存の `*reconcile.Result` をそのまま戻り値として使う。

* MBC PoC のドメイン層は plain `error` を返すが、MB では「成功として終了」「requeue」「slow requeue」「エラー」の四値の表現が必須（`expire` の要求経路、`checkPVCBound` の pending 待ち、優先度待ちの slow requeue など）。ドメイン層は `reconcile.SlowRequeue()` も返せる必要がある（<<risk-priority>> 参照）。
* `internal/controller/internal/reconcile` は他の層に依存しない小さなユーティリティであり、ドメイン層から依存しても new-architecture.adoc の「ドメイン層は他のどの層にもコード上の依存がない」という制約（層への依存の禁止）には反しない。PoC のドメイン層も controller-runtime（`controllerutil`）に依存している前例がある。
* 既存サブフローの戻り値型と一致するため、移行時の書き換え量を最小化できる。

ユースケース層の `Run` は `*reconcile.Result` を返し、インフラ層（`Reconcile`）で `ToCtrlResult()` により `ctrl.Result` へ変換する。

[#d2]
=== D2: 共有定数・純粋ヘルパの移動

MB-C 先頭のラベル・アノテーション・sync-mode・名前プレフィックス定数、および `Make*Name`・`ExtractPartNumFrom*` などの純粋ヘルパ関数は、それらを使用するコンポーネントをドメイン層へ移す PR で、コンポーネントと一緒にドメイン層（`internal/controller/domain`）へ移動する。定数・純粋ヘルパだけを先行して一括移動する PR は設けない。

* これらは「Mantle がどのように振る舞うか」の定義そのものであり、ドメイン層の管轄。
* 移動する定数・純粋ヘルパを `replication.go`・既存 envtest テストなど移動前のコンポーネントも参照している場合、その PR で import 変更のみの機械的修正を行う。
* 複数のコンポーネントから参照される定数・純粋ヘルパは、それを最初に必要とするコンポーネントの移動 PR で移し、後続のコンポーネントは移動済みの定義を利用する。
* `getCephClusterIDFromPVC`（`util.go`）は外部アクセス（StorageClass の読み取り）を持つためドメイン層へは移動せず、インフラ層へ移動する（`mantlerestore_controller.go`・`replication.go` と共有しているため機械的な参照先修正を伴う。<<d6>> 参照）。
* 移動対象には優先度機能・転送圧縮で追加された定数（`LabelBackupPriority`・`labelBackupPriorityHigh`・`transferCompressionZstd`）も含む。`LabelBackupPriority` と `MantleBackupConfigUID` は `cmd/backup` からも参照されるため、移動 PR では `cmd/backup` の参照も機械的に修正する。`MantleBackupConfigUID` は `cmd/backup/main.go` に同じ文字列の定義が重複しているので、移動を機に一本化してよい（値は変えない。<<wire-contract>> 参照）。

[#d3]
=== D3: Operations とインターフェースの使い分け

new-architecture.adoc の方針通り、**書き込み系はドメインイベント（Operation）を優先**し、**呼び出し結果がその場のリコンサイル判定に影響するものだけ**ドメイン層定義の narrow interface を使う。読み取り系は原則ユースケース層が事前に取得してドメイン層へデータとして渡す。分類は次の通り：

[cols="3,2,3", options="header"]
|===
| 外部アクセス | 方式 | 備考

| リコンサイル対象 `MantleBackup` の変更（ラベル・finalizer・アノテーション・status・conditions）
| メモリ上で変更し、ユースケース層が永続化
| PoC と同じ方式。ただし元のオブジェクトとの比較は、メタデータ・spec と status で独立に行う。メタデータ・spec に差分がある場合だけ `Update` を、status に差分がある場合だけ `Status().Update` を呼ぶ。両方に差分がある場合は `Update` を先に行い、その応答で更新された resourceVersion を使って `Status().Update` を行う。先行する永続化に失敗した場合は後続の永続化と Operation 適用を行わない。PoC は `Update` のみ。<<risk-persist-order>> の例外あり

| Job・Pod・PVC・PV の作成／削除、他の `MantleBackup` の更新（diff-from アノテーションなど）、期限切れ backup の削除
| Operation
| Job マニフェスト構築はインフラ層に置く（<<d4>>）

| gRPC `CreateOrUpdatePVC` → `CreateMantleBackup`（レプリケーション）
| 複合 Operation
| 前者のレスポンス（PVC UID）を後者のリクエストが使うが、レスポンスをドメイン層の判定には使わないため、2 呼び出しをまとめた 1 つの Operation としてインフラ層で実行する。なお現行実装は送信直後の同一パス内で `ListMantleBackup` が送信結果を読むため、セカンダリに対象 backup がまだ存在しない初回だけは Operation 化に伴い 2 周のリコンサイルに分解する。対象 backup が存在してから `SnapshotCaptured` になるまでは、現行どおり各リコンサイルで Operation を再発行する（PR 10・<<risk-requeue>> 参照）

| gRPC `SetSynchronizing`
| Operation
| 同一パス内の後続処理はレスポンスに依存しない

| gRPC `ListMantleBackup`（セカンダリの backup 一覧）
| ユースケース層で事前取得
| 無条件取得にすると同期済み backup や先行 backup の同期待ち中にも gRPC 呼び出しが増えるため、段階的に事前取得する。まず primary の backup 一覧を K8s から取得し、ドメイン層の純粋関数で先行する全 backup が同期済みか判定する。対象が未同期かつ先行 backup がすべて同期済みの場合だけ `ListMantleBackup` を呼ぶ

| Job の完了状態・ラベル付き Job/PVC の一覧・対象 PVC の存在
| ユースケース層で事前取得
| `checkJobStatus`・`handleCompletedJobsOfComponent`・`canNewJobBeCreated`・`canNewExportDataPVCBeCreated` 相当の判定はドメイン層で行い、入力（Job/PVC のリスト・状態）はデータとして渡す。`deletePodsOfJob` 内の一覧取得は、不要な DeleteCollection を避けるための Operation 実行時の詳細としてインフラ層に置く

| オブジェクトストレージ `Exists`（secondary でのアップロード済み確認）・`GetSize`（primary のメトリクス）
| ユースケース層で事前取得
| 必要な状態のときだけ取得する。取得の要否はドメイン層の判定関数で決める（後述）。primary の `GetSize` はメトリクス算出専用でリコンサイル判定には使わないため、クライアント初期化または `GetSize` に失敗してもエラーを返さず、現行どおりログを出してメトリクス更新だけをスキップし、verify・レプリケーション・cleanup を継続する

| オブジェクトストレージ `Delete`（secondary cleanup）
| ドメイン層定義の interface
| Provision の通常 cleanup（現行の `secondaryCleanup(_, _, true)` 相当）でのみ行い、Finalize（同 `false` 相当）では行わない。削除の成功が対象 backup のアノテーション更新へ進む条件になるため、Operation にはしない。同期的に削除を実行し、全 part の削除が成功した場合だけ後続へ進む。失敗時は対象 backup を変更せず、次回のリコンサイルで再試行する

| MantleBackupConfig の優先度ラベルの同期（`syncPriorityLabelFromMBC`）
| メモリ上で変更し、ユースケース層が永続化
| リコンサイル対象自身のラベル変更なので、上記 1 行目と同じ扱いにする（現行の `Patch` は廃止する）。MantleBackupConfig の取得はユースケース層で事前取得し、取得の要否（`MantleBackupConfigUID` ラベルの有無）はドメイン層の純粋関数で決める

| 高優先度 backup の待ち判定（`shouldWaitForHigherPriorityBackup`・`shouldWaitForHigherPriorityImport`）
| ユースケース層で事前取得
| 高優先度 backup の一覧（削除中を除く）と、対象 backup が export-data PVC を保有しているか（`doesMantleBackupHoldExportDataPVC` の入力となるラベル付き PVC 一覧）をユースケース層が取得し、待つべきかの判定はドメイン層の純粋関数で行う。いずれも K8s のキャッシュ読み取りなので事前取得してよい。判定結果が真のときドメイン層は slow requeue を返す。判定を入れる位置には順序不変条件がある（<<risk-priority>> 参照）

| RBD スナップショットの作成（作成結果の ID・サイズ・タイムスタンプを status に書く）
| ドメイン層定義の interface
| 呼び出し結果がリコンサイル内容を決めるため。`CreateAndFindRBDSnapshot` のような専用 interface をドメイン層に定義し、インフラ層が `ceph.CephCmd` で実装する

| RBD スナップショットの削除（存在確認 → 削除 → 削除確認、`removeRBDSnapshot`）
| ドメイン層定義の interface
| 読み取り結果で分岐する一連の処理のため

| verify 用 clone イメージの作成（既存クローンと親スナップショットの確認 → 作成）
| ドメイン層定義の interface
| 読み取り結果で分岐する一連の処理のため。インフラ実装は `createCloneByPV` を利用する（<<d6>>）

| インポート済み RBD スナップショットの検索（`markSecondarySnapshotCaptured`）
| ドメイン層定義の interface
| 検索結果（SnapID）を status に書くため

| RBD ボリュームロック（`lockVolume`/`unlockVolume`）
| ドメイン層定義の interface
| ロックは複数リコンサイルパスにわたって保持される（Job 未完了の間は unlock せず requeue し、次パスでは取得済みの自ロックを確認して続行する）ため、Operation では表現できない

| 中間スナップショット削除・verify 用イメージ削除（Ceph）
| ドメイン層定義の interface
| 一覧取得 → 判定 → 削除の複合処理のため
|===

事前取得を条件付きで行う場合（特に gRPC・S3・`rbd` コマンドの呼び出し回数を増やさないための条件）、その要否判定は**ドメイン層に純粋な判定関数**として定義し、ユースケース層はそれを呼び出すだけにする。「どのような状況で何が必要か」はドメインロジックであり、ユースケース層に埋め込まない。判定関数として括り出すことでユニットテストの対象にもなる。判定に追加データが必要な場合は段階的に取得する。例えば `ListMantleBackup` の要否は `NeedsSecondaryBackupList(backup, primaryBackups)` のように primary の backup 一覧も入力とし、先行 backup の同期確認に合格した後だけ gRPC を呼ぶ。判定関数のためのデータを得る目的で、より高コストな外部アクセスを先に実行してはならない。

interface は new-architecture.adoc の指示通り「その処理に必要なメソッドのみ」を定義し、他の処理と共有しない。テストでは gomock（`ceph_mock.go` 相当）ではなく、必要に応じてテスト内で小さな fake を書く。

[#d4]
=== D4: Job マニフェスト構築の置き場所

`createOrUpdateExportJob`（約 180 行）・`createOrUpdateUploadJobs`・`createOrUpdateImportJob`（約 215 行）・`createOrUpdateZeroOutJob`・`createOrUpdateVerifyJob` の Job spec 構築コードは**インフラ層**に置く。

* ドメイン層が発行する Operation（例：`CreateOrUpdateExportJobOperation`）には、判定に由来するパラメータ（Job 名、対象 backup の情報、pool/image/snapshot 名、part 番号、full/incremental、転送サイズ、転送圧縮の形式など）のみを持たせる。
* Pod spec の詳細（コンテナ定義、env、securityContext、スクリプト、proxy 設定、`podImage`・`envSecret`、Job の affinity）は外部システム（Kubernetes）への依存の詳細であり、インフラ層の Operation 実行器が組み立てる。PoC の `CreateOrUpdateMBCCronJobOperation` → `createOrUpdateMBCCronJob` と同じ関係。affinity は `PrimarySettings`・`SecondarySettings` から来るため、Operation 実行器がこれらの設定を保持する（`podImage`・`envSecret`・`proxySettings`・`ExportDataStorageClass` と同じ扱い）。affinity は Operation のパラメータにしない。現行では export/upload/import Job にのみ affinity が設定され、zero-out Job と verify Job には設定されないので、この非対称性をそのまま維持する。
* 一方、転送圧縮の形式（`spec.transferCompression`）は Job spec の詳細に閉じない。`MakeObjectNameOfExportedData` を通じてオブジェクトストレージ上のオブジェクト名を決めるため、Job 作成の Operation に加えて `GetSize`（PR 7・PR 12 のメトリクス）・`Exists`（PR 14 の part 0 アップロード確認）・`Delete`（PR 15 のエクスポートデータ削除）でも層をまたいで渡す必要がある。
* これによりドメイン層のユニットテストは「どの Job をどのパラメータで作ろうとしたか」の検証に集中でき、Job spec の細部はインテグレーション・E2E テスト（既存）に委ねる。

[#d5]
=== D5: その他の配置

`exportedDiffSizeCache`::
メトリクス算出用のメモリ内キャッシュであり、リコンサイルの判定には使われない。primary のユースケース層（`ReconcileMBPrimary` のフィールド）に置く。キャッシュを参照して未取得 part の範囲を決める処理、各 part の `GetSize`、合計値の算出、全 part の取得に成功した後のキャッシュ更新は、可変状態を所有するユースケース層が一続きで行う。ドメイン層は受け取った合計値をメトリクスへ設定するだけとする。途中の part で `GetSize` が失敗した場合はキャッシュを更新しない。

`expireQueueCh`・`scheduleExpire`::
workqueue への遅延投入はインフラ層の関心。ドメイン層は「まだ期限切れでない」ことを判定して `ScheduleExpireOperation` を発行し、インフラ層の実行器がチャネルへ送出する。`SetupWithManager` の `WatchesRawSource` 配線は現状のまま `mantlebackup_controller.go` に残す。

`prepareObjectStorageClient`（S3 クライアントの遅延初期化）::
インフラ層に移す。ConfigMap/Secret から認証情報を読んで `objectstorage.Bucket` を返す処理をインフラ層のコンポーネントとし、ユースケース層はそれを介して `Exists`/`GetSize` の事前取得を行う。ユースケース層からの利用は、PoC の `usecase.KubernetesClient` と同様にユースケース層で定義したインターフェースをインフラ層が実装する形（依存性逆転）とし、new-architecture.adoc の「ユースケース層はインフラ層に依存しない」制約を守る。このコンポーネントは primary のメトリクス復元をユースケース層へ移す PR 7 で導入し、PR 12 の upload メトリクスと PR 14 の secondary `Exists` はそれを利用する。現行の secondary は、`Reconcile` 共通の `checkManagedBackup` を通過した後、ロール固有の所有権スキップ判定より前に、`Exists` の要否にかかわらずクライアントを初期化し、失敗した場合はそのリコンサイル全体を中断する。このエラー経路を変えないため、新実装でも secondary の `Run` は、<<managed-backup-preflight,管理対象の事前判定>>を通過した直後かつ `Provision`/`Finalize` の呼び出しより前にクライアントを初期化する。primary ではクライアント初期化と `GetSize` はメトリクス算出専用であり、失敗時は <<d3>> のとおりリコンサイルを中断しない。

メトリクス出力::
PoC（`MBCPrimaryReconciler.Provision`）と同様、ドメイン層から `metrics` パッケージを直接呼んでよい。`metrics` パッケージは外部システムへのアクセスを持たないため、new-architecture.adoc の層依存の制約には抵触しない。

ユースケース層の初期化::
`NewMantleBackupReconciler` の中でインフラ層の Kubernetes クライアントと 3 ロール分のユースケース層コンポーネントを即時初期化する（PR 2 での実装済みの形）。MBC PoC が `sync.Once` による遅延初期化を用いているのは、その初期化が API サーバへのアクセスを必要とするためであり、MB では現時点で不要である。今後ユースケース層の初期化が API サーバ依存の情報を必要とするようになった場合は、MBC と同様の遅延初期化へ切り替える。

[#managed-backup-preflight]
=== 管理対象の事前判定

現行の `checkManagedBackup` はロール分岐より前に実行され、管理対象外の backup ではロール固有の外部アクセスを行わず成功扱いで終了する。この順序を維持するため、管理対象判定は `Provision`/`Finalize` 内の逐次 `if` ではなく、ユースケース層 `Run` の共通事前判定として実行する。

判定ロジック（`labelClusterID` の一致、ラベル未付与時の PVC の cluster ID 照合）はドメイン層の純粋な判定関数に置き、`Run` はその関数を呼ぶ。PVC と cluster ID は判定に必要な場合だけ `Run` が取得する。管理対象外なら `Run` は成功扱いで終了し、secondary の S3 クライアント初期化を含む後続の事前取得や `Provision`/`Finalize` は実行しない。管理対象なら、secondary は S3 クライアントを初期化してから `Provision`/`Finalize` を呼ぶため、現行の「`checkManagedBackup` → S3 初期化 → ロール固有の所有権ガード」という順序を保つ。

[#d6]
=== D6: 共有ヘルパのインフラ層への移動

`util.go` の `createCloneByPV`・`deleteRBDImageAsynchronously`・`getCephClusterIDFromPVC`（と下請けの `getCephClusterIDFromSCName`）は外部アクセスを持つヘルパであり、MB のドメイン interface のインフラ実装（verify 用 clone 作成・verify イメージ削除）やユースケース層の事前取得（cluster ID）が同じ処理を必要とする。一方でこれらは `mantlerestore_controller.go`・`persistentvolume_controller.go`・`replication.go` とも共有されている。`internal/controller` パッケージは `usecase`・`infra` を import 済みのため、`usecase`・`infra` 側から `internal/controller` のシンボルを参照すると import 循環になり、そのままでは再利用できない。

そこで、これらのヘルパは**エクスポートした上でインフラ層（`internal/controller/infra`）へ移動**し、`internal/controller` 側（他コントローラ・`replication.go`・既存テスト）は infra を参照するように機械的に修正する（`internal/controller` → `infra` の依存は既存のため循環しない）。移動は<<migration-strategy-note,移行戦略>>の方針 4 に従い、それぞれを初めて必要とする PR で行う：`getCephClusterIDFromPVC` は PR 5、`createCloneByPV` は PR 7、`deleteRBDImageAsynchronously` は PR 8。ユースケース層からの利用（PR 5 の cluster ID 取得）は、<<d5>> のオブジェクトストレージクライアントと同様に、ユースケース層で定義したインターフェースをインフラ層が実装する形（依存性逆転）とする。

[#d7]
=== D7: verify とレプリケーションの並行進行（primary）

現行の primary は、verify Job が未完了でも同一リコンサイルパス内でレプリケーション処理へ進む（`verify` は Job 未完了時に requeue ではなく「継続」を返す）。つまり検証とレプリケーションは並行に進行し、e2fsck の完了を待たずに export/upload が始まる。verify 全体を「`if 未verify { return verify 処理 }`」のような終端する 1 つの `if` にするとレプリケーション開始が検証完了まで遅延してしまうため、この形は採らず、verify を次の構造でドメイン化する：

```go
if 未verify かつ verify Job が存在しない {
    return verify リソースの作成  // clone 作成（interface）→ 静的 PV/PVC・verify Job の作成（Operation）→ requeue
}
if 未verify かつ verify Job が完了している {
    Verified condition をメモリ上で更新する  // return せず後続の if へ継続する
}
// 未verify かつ verify Job 実行中の場合は、どの if にも該当せず後続へ継続する

...（primary はここにレプリケーションの if 群）...

if 未verify または（primary で）未同期 {
    return requeue  // cleanup は verify・同期の完了後のみ実行する（現行の挙動と同じ）
}
return cleanup
```

verify Job の存在・完了状態はユースケース層が事前取得したデータで判定する（<<d3>>）。2 つ目の `if` が return しない「継続処理」であることは、expire（PR 5）やメトリクス出力と同様に new-architecture.adoc が許容する逐次 `if` の例外として扱う。cleanup の前の「未verify なら requeue」のガードは、verify Job の実行中に cleanup が verify リソース（Job・PV/PVC・clone）を削除してしまうことを防ぐために必須である。この構造により：

* primary では verify Job の実行中・完了のパスでも後続のレプリケーションの `if` に到達し、現行どおり検証とレプリケーションが並行進行する。standalone・secondary では verify の後続はガードと cleanup のみである。
* verify リソース作成の `if` は return するため、現行（作成と同一パスでレプリケーションも進む）に比べ検証開始パスでリコンサイルが 1 周増える（<<risk-requeue>> の許容例外）。
* 現行は未 verify の間、毎パスで clone・静的 PV/PVC・Job を再確認・再作成していた（`rbd ls` も毎パス発行される）が、新実装では verify Job が存在しない場合のみ作成する。Ceph への呼び出しが減る方向の変化であり許容する。
* 完了パスでは condition をメモリ上で更新して継続するため、verify 完了後の余分な 1 周が消える（<<risk-requeue>> 参照）。

[#d8]
=== D8: export-data PVC 上限と完了 part のリソース解放

primary の `--max-export-data-pvcs` は、managed Ceph cluster の namespace に同時に存在できる export-data PVC 数を制限する。リファクタリング後も次の挙動を維持する：

* `MaxExportDataPVCs == 0` は無制限とする。上限が有効な場合、新しい part の PVC が既に存在すれば、全体の PVC 数が上限以上でも対応する export Job の作成・更新を続行する。PVC が存在しない場合だけ、同 namespace の `app.kubernetes.io/name=mantle` かつ `app.kubernetes.io/component=export-data` の PVC を数え、上限未満なら作成する。削除中の PVC も backing PV が領域を消費しうるため数に含める。
* upload Job が完了した part は、最新の完了 part を含めて export-data PVC を直ちに削除する。最新の完了 upload Job は進捗管理のため残す一方、その part の export Job・upload Job の Pod は削除し、pvc-protection によって PVC が Terminating のままスロットを占有し続けることを防ぐ。最新でない完了 Job は従来どおり Job 自体の削除により Pod も削除される。
* `MaxExportDataPVCs` は primary の設定としてユースケース層・ドメイン層へ渡す。対象 part の PVC、ラベル付き PVC 一覧、完了 Job の状態はユースケース層が事前取得し、作成可否と解放対象はドメイン層が判定する。PVC・Pod の削除は Operation とし、現行どおり PVC の削除要求後に最新完了 part の Pod を削除する順序で発行する。Pod の一覧取得と DeleteCollection は Operation 実行器が一続きで行う。
* **export-data PVC を 1 つでも保有している backup は、優先度ゲートで待たせない**（`doesMantleBackupHoldExportDataPVC`。削除中の PVC も保有とみなす）。占有されたスロットは、その backup 自身のリコンサイルが進まない限り解放されないため、待たせると高優先度の backup を含む全 backup が永久に進めなくなる。

この挙動を崩すと、特に `MaxExportDataPVCs == 1` の multi-part backup で、前 part の PVC がスロットを占有して次 part の PVC を作れないデッドロックが発生する。また最後の箇条を崩すと、低優先度 backup がスロットを保持したまま高優先度 backup を待ち、その高優先度 backup はスロットの解放を待つという循環待ちが発生する。PR 11（PVC 上限の判定）と PR 12（優先度ゲートの配線）では既存の envtest・E2E テストに加え、ドメイン層のユニットテストでこれらの不変条件を担保する。優先度ゲートの順序不変条件は <<risk-priority>> も参照。

== 段階的移行計画

[#migration-strategy-note]
=== 移行戦略

ストラングラーフィグパターンに基づき、次の方針で進める：

1. **最初に最終形と同じ呼び出し経路（`Reconcile` → `usecase.Run` → 管理対象の事前判定 → `domain.Provision`/`Finalize`）を骨組みとして導入する**（PR 2 で何もしないスケルトンと呼び出し経路を、PR 3 で legacy 委譲の仕組みを導入する。実装では両者を 1 つの PR としてマージした。<<diff-pr3-policy>> 参照）。ドメイン層の関数を旧コードから直接呼ぶ中間状態は作らず、ドメイン化された処理は常にユースケース層経由で実行される。管理対象の事前判定は PR 5 でこの経路に追加する。
2. 移行が完了していない状況に対しては、`Provision`/`Finalize` が「旧コードに委譲する」ことを表す一時的な戻り値（以下 **legacy 委譲シグナル**）を返す。`Run` は、そこまでにドメイン層が行ったリコンサイル対象の変更の永続化と Operations の適用を済ませた上でシグナルを呼び出し元へ伝え、`Reconcile` が旧コード経路を実行する。
3. サブフローを 1 つずつドメイン化し、`Provision`/`Finalize` の逐次 `if` に追記していく。ドメイン化したサブフローの旧コードは同じ PR で削除する。あるロールの全サブフローが揃ったら、そのロールの legacy 委譲シグナルと旧コード経路を削除する。従来方式のような「一括切り替え PR」は不要になり、ロール完成時の PR は削除が主体の低リスクなものになる。
4. Operation 型・インフラ層の Operation 実行器・ドメイン interface のインフラ実装、および定数・ヘルパは、先行 PR でまとめて移動・導入せず、**それらを使用するコンポーネントを移す PR で一緒に移動・追加する**。複数のコンポーネントで共有する定数・ヘルパは最初の利用コンポーネントの移動時に移す。レビュー時に利用側と定義・実行側を突き合わせて確認できるようにするためでもある。この方針は、`Run` の Operations 引き渡し機構（PR 5 で導入）と `Run` の永続化機構（PR 6 で導入）そのものにも適用する（<<diff-pr3-policy>> 参照）。
5. ロールは standalone → primary → secondary の順に完成させる。standalone のフローは primary の部分集合（ローカルバックアップ＋verify＋cleanup）なので、共有部分のドメイン化がそのまま primary の下準備になる。

「最初からユースケース層経由」での移行が可能な理由と、そのために必要な一時的な仕組みは次の通り：

* `Provision`/`Finalize` は「`if 条件 { return 処理 }` の逐次実行」であり、原則として 1 回のリコンサイルは最初に成立した条件の処理だけを実行して終わる（expire や verify の condition 更新のような、処理をしても return しない「継続処理」の例外はある。PR 5・<<d7>> 参照）。そのため「移行済みの条件の `if`」と「未移行の状況で legacy 委譲シグナルを返す `if`」が同じ関数内に矛盾なく共存でき、サブフローをフロー順に縛られることなく 1 つずつ移行できる。
* legacy 委譲シグナルは一時的な戻り値であり、全ロールの移行完了時（PR 16）に仕組みごと削除する。実装では `internal/controller/internal/reconcile` の `Result` に持たせた（<<plan-impl-diff>> 参照）。
* 例外として、primary でリコンサイルごとに実行されるメトリクス復元処理（`setExportedDiffSizeMetric` 系。現状は所有権ガード・expire・deletionTimestamp 確認・ローカルバックアップ処理の後、verify とレプリケーションの前に実行される）は「条件で終端する処理」ではないため逐次 `if` に馴染まない。`usecase.Run` より前へ巻き上げると、本来は所有権スキップやローカルバックアップのエラーで到達しない backup に対して K8s/S3 アクセスが発生するため、その形は採らない。PR 7 で `exportedDiffSizeCache` とともに primary のユースケース層へ移し、管理対象判定・所有権ガード・expire・deletionTimestamp 確認・ローカルバックアップ処理がすべて後続へ進める状態であることをドメイン層の純粋関数で確認した後、verify の事前取得・判定より前に実行する。なお現行の `reconcileAsPrimary` は「ローカルバックアップ → メトリクス復元 → verify → （未同期なら）`syncPriorityLabelFromMBC` → `replicate` → 未完了なら requeue → cleanup」の順であり、優先度ラベルの同期は未同期分岐の中にある（そのドメイン化は PR 12 で行う）。キャッシュを使った増分取得の責務は <<d5>> に従う。PR 7 では旧 `reconcileAsPrimary` のメトリクス復元ブロックに加え、legacy `startUpload` 内の同じメトリクス更新呼び出しも削除し、キャッシュ所有権と更新経路をユースケース層へ一本化する。いずれも同一リコンサイル開始時に存在する完了 upload Job を入力とするため、ユースケース層の復元処理が同じ最大完了 part を先に観測できる。

この戦略により、どの時点でも未移行の経路は旧コードが現役で動き続け、各 PR のレビュー範囲が「1 サブフローのドメイン化とそのテスト」に限定される。

==== PR 5: expire と checkManagedBackup のドメイン化

* **内容**: `expire` の判定ロジック（CreatedAt 未設定・deletionTimestamp・retain-if-expired アノテーション・期限計算）をドメイン化し、削除は `DeleteMantleBackupOperation`、遅延 requeue は `ScheduleExpireOperation` として発行する。`checkManagedBackup` の判定部分（ラベル一致・cluster ID 照合）もドメイン層の純粋な判定関数としてドメイン化し、これらの処理が使用する定数・純粋ヘルパを同じ PR でドメイン層へ移動した上で、<<managed-backup-preflight>> のとおり `Run` が `Provision`/`Finalize` より前に呼び出す。PVC と cluster ID の取得はユースケース層（`Run`）が行う。cluster ID の取得はユースケース層定義のインターフェース経由とし、その実装としてインフラ層へ移動した `getCephClusterIDFromPVC` を用いる（<<d6>>。`mantlerestore_controller.go`・`replication.go`・既存テストの参照は機械的に修正する）。PVC の取得は従来どおり `labelClusterID` 未付与の場合にのみ行い（要否はドメイン層の判定関数で決める）、NotFound はエラーとせずデータとしてドメイン層へ渡す（無条件取得＋NotFound を requeue にすると、PVC 削除済み backup の finalize が進まなくなるため）。管理対象外ならロール固有の事前取得を行わず成功扱いで終了する。実装では `checkManagedBackup` が `Reconcile` の中で `usecase.Run` より前に呼ばれているので、**この PR で `Reconcile` 側の呼び出しを削除し `Run` へ移す**（<<plan-impl-diff>> 参照）。expire の `if` は全ロールの `Provision` の所有権ガードの後へ追記する。expire は deletionTimestamp が付いた backup では何もしないため、`Finalize` への追記は不要。旧 `expire`・`checkManagedBackup` は削除する。`Run` の Operations 引き渡し機構（ドメイン層の `ReconcilerOperations` フィールド、ユースケース層が定義する適用インターフェース）、両 Operation の型、インフラ層の実行器（`expireQueueCh` の注入を含む）をこの PR でまとめて追加する（PR 3 から繰り延べられた分。<<diff-pr3-policy>> 参照）。MB 用の Operation 適用は「発行順に実行し、失敗したら残りを打ち切る」契約とし、この PR で定める（<<risk-op-order>> 参照）。なお expire は、未失効の場合に `ScheduleExpireOperation` を発行した上で後続の `if` へ処理を続ける。これは「`if 条件 { return 処理 }`」の逐次実行に馴染まない継続処理だが、Operation の発行のみで判定には影響しないため、メトリクス出力と同様に new-architecture.adoc が許容する例外として扱う。
* **テスト**: 「管理対象外ならロール固有の事前取得を行わず成功する」「管理対象の secondary では S3 初期化より先に管理対象判定を行う」「期限切れなら削除 Operation を発行する」「retain-if-expired なら何もしない」「未期限なら schedule Operation を発行する」「PVC NotFound なら requeue する」等の AAA ユニットテスト。加えて、この PR で導入する Operations 引き渡し機構に対して「発行順に実行される」「途中で失敗したら残りを打ち切る」ことのユニットテストを書く。MB 用のユニットテストはこの PR が最初になるため、`domain/mbc_primary_reconciler_test.go` のスタイル（AAA・testify・`t.Parallel()`・functional options によるフィクスチャビルダ）を MB 用にも確立する。
* **規模**: 小〜中。Operation を用いる最初のサブフロー移行としてパターンを確立する PR。

==== PR 6: ローカルバックアップ準備とスナップショット作成のドメイン化

* **内容**:
** `reconcileLocalBackup` のうち、ラベル（cluster-id / local-backup-target-pvc-uid）と finalizer の付与、`getSnapshotTarget` の判定部分（PVC UID 照合、`checkPVCBound`、PV からの image/pool 抽出）をドメイン化する。PVC・PV の取得はユースケース層が行いドメイン層へ渡す。
** `provisionRBDSnapshot` を「2 周のリコンサイル」に分解してドメイン化する（<<risk-persist-order>> 参照）：第 1 周はラベル（cluster-id / local-backup-target-pvc-uid）・finalizer・PVC/PV マニフェスト（status）をメモリ上でセットして requeue（永続化はユースケース層）、第 2 周はこれらの永続化済みを確認してから `CreateAndFindRBDSnapshot` interface（この PR でドメイン層に定義、インフラ層で `ceph.CephCmd` により実装）でスナップショットを作成し、SnapID・CreatedAt・SnapSize・conditions をメモリ上で更新する。
** 以上を standalone・primary の `Provision` の `if` として追記し、旧コードの該当部分を削除する。
** `Run` の永続化機構をこの PR で導入する（PR 3 から繰り延べられた分。<<diff-pr3-policy>> 参照）。すなわち、`Provision`/`Finalize` の呼び出し前に DeepCopy を取り、メタデータ・spec と status の dirty 判定を独立に行う。メタデータ・spec に差分がある場合だけ `Update`、status に差分がある場合だけ `Status().Update` を行い、両方に差分がある場合はこの順序で実行して更新後の resourceVersion を引き継ぐ。先行する永続化に失敗した場合は後続の永続化と Operations を実行しない。現行コードが競合対策として用いている再取得つき status 更新・`Patch` に相当する競合時の方針（conflict エラーを requeue に任せる、再取得してリトライする等）もこの PR で定める。
** あわせて、legacy 委譲でフォールバックした旧コードが古い `MantleBackup` を触らないようにする。実装では `Reconcile` と `Run` がそれぞれ `MantleBackup` を取得しているため、`Run` が永続化を行うようになるとこの二重取得が問題になる（<<plan-impl-diff>>・<<risk-legacy>> 参照）。`Run` が更新後のオブジェクトを呼び出し元へ返すか、legacy 委譲時に `Reconcile` 側で再取得するかのいずれかで対処する。
* **テスト**: ラベル・finalizer 付与、マニフェスト未保存時の requeue、スナップショット作成後の status 更新、fake interface を使った作成失敗時の挙動。加えて `Run` の永続化機構について、メタデータ・spec のみの変更では `Update` だけを呼ぶこと、status のみの変更では `Status().Update` だけを呼ぶこと、両方の変更では `Update` → `Status().Update` の順序で実行し resourceVersion を引き継ぐこと、先行する永続化が失敗したら後続の永続化と Operations を実行しないこと、finalizer 除去だけのパスで `Status().Update` を呼ばないこと。
* **規模**: 中。ドメイン interface を使う最初の PR であり、`Run` の永続化機構を導入する PR でもある。
* **備考**: `syncPriorityLabelFromMBC` による優先度ラベルの同期は、この PR の対象ラベル（cluster-id・local-backup-target-pvc-uid）ではなく primary の未同期分岐の中で行われる処理なので、PR 12 で扱う。

== リスク・注意点

[#risk-persist-order]
=== status 永続化と Ceph 操作の順序不変条件

`provisionRBDSnapshot` は「PVC/PV マニフェストを status に**永続化した後に** RBD スナップショットを作成する」ことでクラッシュ時の孤児スナップショットを防いでいる（MB-C 内コメント参照）。「変更をメモリ上に溜めて `Run` の最後に一括永続化」する標準パターンではこの不変条件が壊れる。同種の不変条件として「ラベル（local-backup-target-pvc-uid）・finalizer を永続化した後にスナップショットを作成する」もある（`labelClusterID` 定数のコメントおよび `reconcileLocalBackup` のラベル付与コメント参照）。PR 6 の通り、リコンサイルを 2 周（ラベル・finalizer・マニフェストの永続化 → 次周でスナップショット作成）に分けることで、これらの不変条件を保ちながらドメイン化する。リコンサイルが 1 周増えるが、外部から見た状態遷移の順序は変わらない。同様に「途中で永続化してから次の外部操作を行う」箇所が他にないか、各 PR で移行対象コードを精査すること。

[#risk-finalize-order]
=== クリーンアップ・ファイナライズにおける外部作用と対象の永続化の順序

<<risk-persist-order>> とは逆向きの順序不変条件として、`primaryCleanup`・`secondaryCleanup`・`finalizeStandalone`・`finalizeSecondary` は「**他リソースへの外部作用を完了してから**、対象 backup 自身の変更を永続化する」順序に依存している。具体的には：

* source backup の diff-to アノテーション削除は、対象 backup の diff-from アノテーション削除（の永続化）より前に行われる。逆順にすると、間でクラッシュや Operation の失敗が起きた場合に diff-from が先に消え、以降のリコンサイルは source を特定できなくなる。source には diff-to が残り続け、`finalize*` は diff-to があると何もしないため、source の finalize が永久にブロックされる。
* finalizer の除去は、Job・PVC・PV と RBD スナップショットの削除がすべて完了した後に永続化される。逆順にすると、finalizer 除去の永続化と同時に MantleBackup が消滅するため、その後の削除 Operation が失敗・クラッシュした場合にリソースがオーファン化し、それを再試行するリコンサイルも存在しなくなる。

一方、ユースケース層の `Run` の標準的な順序は「対象の永続化 → Operations の適用」であり（new-architecture.adoc）、素朴に 1 パスでドメイン化するとこの順序が逆転する。そこで cleanup・finalize は次のように**複数パスに分解**する：

* 削除対象（source の diff-to アノテーション、cleanup 対象の Job・PVC・PV）が事前取得データ上に残っている間は、削除 Operation を発行して requeue し、対象 backup 自身は変更しない。
* それらがすべて消えたことを確認できたパスで、secondary の Provision cleanup ではオブジェクトストレージ上のエクスポートデータを interface で同期的に削除する。全 part の削除に成功した場合だけ、対象 backup 自身の変更（diff-from・sync-mode アノテーションの削除）へ進んで requeue する。削除に失敗した場合は対象を変更せずエラーを返すため、次回のリコンサイルで再試行できる。Finalize では現行の `deleteExportData=false` を維持し、オブジェクトストレージ削除を行わずに対象アノテーションを削除して requeue する。
* 対象 backup のアノテーション削除が永続化された次のパスで、中間スナップショット削除を interface で同期実行する。これにより現行の「対象アノテーションの永続化 → 中間スナップショット削除」の順序を維持する。すでにアノテーションが削除済みの場合も同じパスから再開できる。
* 中間スナップショット削除の成功後、finalize では RBD スナップショット削除（interface・同期実行）・メトリクス削除・finalizer 除去を行う。このパスでは、対象の変更より先に完了していなければならない Operation を発行しない。

これにより `Run` の標準順序（永続化 → Operations）のままで現行の順序不変条件を保てる。オブジェクトストレージ削除は Provision cleanup に限って `Delete` 呼び出しの成功をゲートにするだけであり、削除後の `Exists` など追加の S3 読み取りは行わない。中間スナップショット削除は対象アノテーションの永続化後に、interface 内で一覧取得・判定・削除を同期的に実行する。K8s リソースの削除がキャッシュへ反映されるのを待つ分と中間スナップショット削除を次パスへ分ける分、cleanup・finalize のリコンサイルが現行の 1 パスから複数パスに増える（<<risk-requeue>> の許容例外）。

=== 結果に依存する外部呼び出しとロック保持

`createRBDSnapshot`（作成結果を同一パス内で status へ反映）、`lockVolume`/`unlockVolume`（複数リコンサイルパスにわたるロック保持）などは Operation では表現できない。これらは無理に Operation 化せず、ドメイン層定義の narrow interface で扱う（<<d3>>）。Operation 化と interface 化の判断に迷ったら「呼び出し結果がその場の判定・出力に使われるか、またはリコンサイルパスをまたいで保持すべき状態か」を基準にする。

[#risk-op-order]
=== Operation 実行の順序と失敗時の打ち切り

PoC の `infra.KubernetesClient.ApplyReconcilerOperations` は、Operation が失敗しても `errors.Join` で後続の実行を続ける。一方 MB には「diff-to アノテーションの付与 → `SetSynchronizing` → export Job 作成」のように、先行の失敗時に後続を実行してはならない順序依存の Operation 列がある。MB 用の Operation 適用は「発行順に実行し、失敗したら残りを打ち切る」契約とし、最初に Operation 実行器を導入する PR 5 で定める。その際 MBC 側の既存挙動を変えないこと（実行器を分けるか、MBC も打ち切りセマンティクスへ統一して問題ないかは PR 5 で判断する）。

なおこの打ち切り契約は、new-architecture.adoc の「渡されたイベントが複数ある場合、エラーの有無に関わらず全てのイベントの実行を試行する」という記述からの**意図的な逸脱**である。PR 5 で契約を定める際、new-architecture.adoc 側にも「順序依存の Operation 列を持つリコンサイラでは失敗時の打ち切りを許容する」旨の例外を追記する。

=== 事前取得によるアクセス増加

読み取りをユースケース層の事前取得に変えると、従来は条件付きだった K8s/gRPC/S3 アクセスが毎回発生しうる。K8s の読み取りはキャッシュ経由のため増加は許容するが、**gRPC・S3・`rbd` コマンドの呼び出し回数は増やさない**こと。取得の要否は、従来と同じ条件を実装したドメイン層の判定関数（純粋関数）をユースケース層から呼び出して決める。判定条件そのものをユースケース層に書いてはならない（ドメインロジックの漏出を防ぎ、判定にユニットテストを書けるようにするため。<<d3>> 参照）。

[#risk-legacy]
=== legacy 委譲境界のリスク

移行期間中は「どの状況をドメイン層が処理し、どの状況を旧コードに委譲するか」の境界が PR ごとに動く。委譲を判定する `if` 条件が削除した旧コードの分岐条件と一致していないと、特定の状況がどちらの経路でも処理されない（または二重に処理される）恐れがある。サブフロー移行 PR のレビューでは、追記した `if` 条件・legacy 委譲条件・削除した旧コードの分岐条件の対応を必ず突き合わせる。

加えて、実装上の次の 2 点に注意する：

* `reconcile.Result.ShouldReturn()` は legacy 委譲シグナルを見ない（`finished`・`requeueing`・`slowRequeueing`・`err` だけを見る）。そのため `Run` の中に `*reconcile.Result` を返す下請けヘルパを追加し、`if result.ShouldReturn() { return result }` だけで受けると、legacy 委譲シグナルが「継続」として素通りし、最終的に `ToCtrlResult()` で「完了・エラーなし」に落ちてリコンサイルがサイレントに打ち切られる。legacy を伝播させるヘルパでは `ShouldContinueWithLegacyReconcile()` も併せて確認する。
* `Reconcile` と `usecase.Run` はそれぞれ独立に `MantleBackup` を取得している。`Run` が永続化を行うようになる PR 6 以降は、legacy 委譲でフォールバックした旧コードが `Reconcile` 側の古いオブジェクトを触る恐れがある。PR 6 で `Run` が更新後のオブジェクトを返すか、legacy 委譲時に `Reconcile` 側で再取得するかを決める（<<plan-impl-diff>> 参照）。ロール完成 PR（PR 9・13・16）はロジック変更を含まない削除主体の PR とし、既存のインテグレーション・E2E テストの通過をもって等価性を確認する。

[#risk-requeue]
=== requeue タイミングの等価性

旧コードの `reconcile.Requeue()` は `REQUEUE_RECONCILIATION_AFTER` 環境変数由来の遅延を持ち、`reconcile.SlowRequeue()` は `SLOW_REQUEUE_RECONCILIATION_AFTER` 由来のより長い遅延を持つ（未設定の場合は前者にフォールバックする）。ドメイン化の際に requeue の発生箇所・回数・種別が変わると、バックアップ完了までの時間が観測可能に変わりうる。原則として旧コードと同じ箇所で同じ種別の結果を返すこと。とくに**優先度待ちの `SlowRequeue` を通常の `Requeue` に変えてはならない**（高優先度の backup を待つ間にリコンサイルを高頻度で回さないための遅延である。<<risk-priority>> 参照）。ただし次の例外は許容する：

* PR 6：`provisionRBDSnapshot` の 2 周分解により、スナップショット作成までのリコンサイルが 1 周増える。また、逐次 `if` の「処理を実行したら return する」構造により、従来 1 パス内で連続実行されていたサブフローの境界（スナップショット作成 → verify 開始など）でもそれぞれ 1 周増える。
* PR 7：verify リソース作成の `if` が return するため、検証開始パスでリコンサイルが 1 周増える（現行は作成と同一パスでレプリケーションも進行する。<<d7>> 参照）。
* PR 8・15：cleanup・finalize の複数パス分解（<<risk-finalize-order>>）により、アノテーション削除・finalizer 除去が削除完了の確認後のパスへ移り、リコンサイルが数周増える。
* PR 10・12：マニフェスト同期の 2 周分解により、初回同期のリコンサイルが 1 周増える。また「セカンダリに対象 backup が見つからない」場合に Failed としていた経路が正常な requeue に変わる。セカンダリに対象 backup が存在してから `SnapshotCaptured` になるまでは現行どおりマニフェストを再送し、`SnapshotCaptured` 後は再送しない（PR 10 参照）。
* 現行は verify 完了後に余分なリコンサイルが 1 周発生している。原因はロールにより異なる：primary では `updateMantleBackupCondition` が DeepCopy に対する `Patch` を行うためメモリ上の backup に結果が反映されず、後続の判定が古い condition を見て requeue する。standalone・secondary では verify 呼び出し後に無条件で requeue を返すコードになっており、`Patch` の反映有無とは無関係に発生する。メモリ上で変更する標準パターンと <<d7>> の構造への移行により、いずれの余分な 1 周も消える（requeue が減る方向の変化）。後者の解消は `Patch` 問題の副産物ではなく「無条件 requeue の削除」という意図的な変更であることに注意する。PR 7・9・13・16 の等価性確認ではこの差を織り込む。

[#risk-priority]
=== 優先度ゲートの順序不変条件

backup priority 機能は、低優先度の backup が高優先度の backup の完了を待つゲートを primary の `replicate` と secondary の `startImport` に持つ。これらのゲートの位置と例外条件はデッドロックを避けるために意図的に選ばれており、ドメイン化の際に逐次 `if` の順序を変えてはならない。

* **primary（`shouldWaitForHigherPriorityBackup`。PR 12）**: 「セカンダリで既に `SnapshotCaptured` になっているかの確認」の**後**、export/upload の判定の**前**に置く。前に出すと、既に同期が完了している低優先度 backup が自分自身を `SyncedToRemote` にできず、永久に待ち続ける。
* **secondary（`shouldWaitForHigherPriorityImport`。PR 14）**: status マニフェストの更新の**後**、ボリュームロックの取得の**前**に置く。後ろに出すと、待っている低優先度 backup がロックを保持し続ける。
* **export-data PVC 保有中は待たない**: export-data PVC を 1 つでも保有している backup は待たせない（削除中の PVC も保有とみなす）。占有されたスロットはその backup 自身のリコンサイルでしか解放されないため、待たせると高優先度の backup を含む全 backup が進めなくなる（<<d8>> の該当箇条を参照）。
* **同一 PVC の高優先度 backup は待ち対象から除外する**: マニフェスト同期には「同一 PVC の先行 backup がすべて同期済みか」という SnapID 順序のゲート（`replicateManifests`。PR 10）もある。同一 PVC 上で古い低優先度 backup と新しい高優先度 backup が並ぶと、優先度ゲートと SnapID 順序ゲートが相互に待ち合ってデッドロックする。これを避けるため、待ち対象の判定では同一の `labelLocalBackupTargetPVCUID` を持つ高優先度 backup を除外する。secondary の import 側も同様。
* 削除中（`deletionTimestamp` あり）の高優先度 backup は待ち対象に含めない（進行しないため待っても解消しない）。

SnapID 順序ゲートのドメイン化は PR 10、優先度ゲートの配線は PR 12 と別 PR に分かれる。移行の各段階で相互待ちが生じないことを、既存の envtest のデッドロック回帰テストとドメイン層のユニットテストの双方で確認する。

[#wire-contract]
=== 定数移動のワイヤ契約

各コンポーネントの移動 PR で一緒に移動する定数は primary↔secondary 間の通信・リソース契約であり、**値の変更は一切禁止**。移動時は文字列リテラルの diff がないことをレビューで確認する。対象には次も含む：

* `LabelBackupPriority`・`labelBackupPriorityHigh`（primary が送信するマニフェストへコピーされ、セカンダリ側でも参照される）。`LabelBackupPriority` と `MantleBackupConfigUID` は `cmd/backup` からも参照される（<<d2>> 参照）。
* `transferCompressionZstd` と、それに対応するオブジェクト名のサフィックス（`.zst`）。オブジェクト名は primary が書き secondary が読むため、値を変えると既存のエクスポートデータを参照できなくなる。
