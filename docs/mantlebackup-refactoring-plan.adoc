= mantlebackup_controller.go 段階的リファクタリング計画

== 目的

link:new-architecture.adoc[Mantle（再）設計案]の三層アーキテクチャ（ドメイン層・ユースケース層・インフラ層）に従い、`internal/controller/mantlebackup_controller.go`（約 3,900 行、以下 MB-C）をリファクタリングする。ねらいは、リコンサイラが次に何を行うべきかの判定を外部リソースへのアクセスから分離し、その振る舞いを envtest に依存しない Arrange-Act-Assert のユニットテストで担保することである。

MantleBackupConfig コントローラで実施済みの PoC（ https://github.com/cybozu-go/mantle/pull/244[PR #244] 他。`internal/controller/domain`・`usecase`・`infra` パッケージ）のパターンを正とし、同じディレクトリ・同じ流儀で実装する。

移行は https://martinfowler.com/bliki/StranglerFigApplication.html[ストラングラーフィグパターン]で進める。各 PR は単体でマージしても外部から見た振る舞いや機能を損ねず、コンパイルが通る。その代わり、PR 単体では nop になるコード（後続 PR から使われるコード）を許容する。

== PR 一覧

ストラングラーフィグパターンに基づき、次の方針で進める。

1. **最初に最終形と同じ呼び出し経路（`Reconcile` → `usecase.Run` → 管理対象の事前判定 → `domain.Provision`/`Finalize`）を骨組みとして導入する**（PR 2・3）。ドメイン層の関数を旧コードから直接呼ぶ中間状態は作らず、ドメイン化された処理は常にユースケース層経由で実行される。管理対象の事前判定は PR 5 でこの経路に追加する。
2. 移行が完了していない状況では、`Provision`/`Finalize` が「旧コードに委譲する」ことを表す一時的な戻り値（**legacy 委譲シグナル**。`internal/controller/internal/reconcile` の `Result` が持つ）を返す。`Run` は、そこまでにドメイン層が行ったリコンサイル対象の変更の永続化と Operations の適用を済ませた上でシグナルを呼び出し元へ伝え、`Reconcile` が旧コード経路を実行する。この仕組みは PR 16 で削除する。
3. サブフローを 1 つずつドメイン化し、`Provision`/`Finalize` の逐次 `if` に追記していく。ドメイン化したサブフローの旧コードは同じ PR で削除する。あるロールの全サブフローが揃ったら、そのロールの legacy 委譲シグナルと旧コード経路を削除する。
4. Operation 型・インフラ層の Operation 実行器・ドメイン interface のインフラ実装、定数・ヘルパ、`Run` の Operations 引き渡し機構（PR 5）と永続化機構（PR 6）は、先行 PR でまとめて導入せず、**それらを使用するコンポーネントを移す PR で一緒に移動・追加する**。
5. ロールは standalone → primary → secondary の順に完成させる。standalone のフローは primary の部分集合（ローカルバックアップ＋verify＋cleanup）なので、共有部分のドメイン化がそのまま primary の下準備になる。

依存関係は原則「番号順」だが、PR 10〜13（primary 系）と PR 14〜15（secondary 系）は互いに独立しており並行して進められる。双方が使用するオブジェクトストレージクライアントのインフラ層コンポーネントは PR 7 で導入済みとする（<<d5>>）。

.「最初からユースケース層経由」での移行が可能な理由
[%collapsible]
====
* `Provision`/`Finalize` は「`if 条件 { return 処理 }` の逐次実行」であり、原則として 1 回のリコンサイルは最初に成立した条件の処理だけを実行して終わる（expire や verify の condition 更新のような、処理をしても return しない「継続処理」の例外はある）。そのため「移行済みの条件の `if`」と「未移行の状況で legacy 委譲シグナルを返す `if`」が同じ関数内に矛盾なく共存でき、サブフローをフロー順に縛られることなく 1 つずつ移行できる。
* 例外として、primary でリコンサイルごとに実行されるメトリクス復元処理（`setExportedDiffSizeMetric` 系）は「条件で終端する処理」ではないため逐次 `if` に馴染まない。`usecase.Run` より前へ巻き上げると、本来は所有権スキップやローカルバックアップのエラーで到達しない backup に対して K8s/S3 アクセスが発生するため、その形は採らない。PR 7 の扱いを参照。
* この戦略により、どの時点でも未移行の経路は旧コードが現役で動き続け、各 PR のレビュー範囲が「1 サブフローのドメイン化とそのテスト」に限定される。
====

=== PR 5: expire と checkManagedBackup のドメイン化

内容::
+
--
* `expire` の判定ロジック（CreatedAt 未設定・deletionTimestamp・retain-if-expired アノテーション・期限計算）をドメイン化し、削除は `DeleteMantleBackupOperation`、遅延 requeue は `ScheduleExpireOperation` として発行する。`if` は全ロールの `Provision` の所有権ガードの後へ追記する。deletionTimestamp が付いた backup では何もしないため `Finalize` への追記は不要。未失効の場合は `ScheduleExpireOperation` を発行した上で後続の `if` へ処理を続ける（return しない継続処理。Operation の発行のみで判定には影響しないため許容する）。
* `checkManagedBackup` の判定部分（ラベル一致・cluster ID 照合）をドメイン層の純粋な判定関数とし、<<managed-backup-preflight>> のとおり `Run` が `Provision`/`Finalize` より前に呼び出す。`Reconcile` にある `checkManagedBackup` の呼び出しは削除して `Run` へ移す。PVC と cluster ID の取得はユースケース層が行う。cluster ID の取得はユースケース層定義のインターフェース経由とし、その実装としてインフラ層へ移動した `getCephClusterIDFromPVC` を用いる（<<d6>>。`mantlerestore_controller.go`・`replication.go`・既存テストの参照は機械的に修正する）。PVC の取得は `labelClusterID` 未付与の場合にのみ行い（要否はドメイン層の判定関数で決める）、NotFound はエラーとせずデータとしてドメイン層へ渡す（無条件取得＋NotFound を requeue にすると、PVC 削除済み backup の finalize が進まなくなるため）。管理対象外ならロール固有の事前取得を行わず成功扱いで終了する。
* `Run` の Operations 引き渡し機構（ドメイン層の `ReconcilerOperations` フィールド、ユースケース層が定義する適用インターフェース）、両 Operation の型、インフラ層の実行器（`expireQueueCh` の注入を含む）をこの PR で追加する（PR 3 から繰り延べられた分）。
* MB 用の Operation 適用は「**発行順に実行し、失敗したら残りを打ち切る**」契約とする。MB には「diff-to アノテーションの付与 → `SetSynchronizing` → export Job 作成」のように、先行の失敗時に後続を実行してはならない順序依存の Operation 列があるため。PoC の `infra.KubernetesClient.ApplyReconcilerOperations` は失敗しても `errors.Join` で後続を続けるので、MBC 側の既存挙動を変えないこと（実行器を分けるか、MBC も打ち切りセマンティクスへ統一して問題ないかはこの PR で判断する）。
* 上記の処理が使用する定数・純粋ヘルパは同じ PR でドメイン層へ移動する（<<d2>>）。旧 `expire`・`checkManagedBackup` は削除する。
--
テスト:: 「管理対象外ならロール固有の事前取得を行わず成功する」「管理対象の secondary では S3 初期化より先に管理対象判定を行う」「期限切れなら削除 Operation を発行する」「retain-if-expired なら何もしない」「未期限なら schedule Operation を発行する」「PVC NotFound なら requeue する」。加えて Operations 引き渡し機構の「発行順に実行される」「途中で失敗したら残りを打ち切る」。

+
--
* 打ち切り契約は link:new-architecture.adoc[Mantle（再）設計案]の「渡されたイベントが複数ある場合、エラーの有無に関わらず全てのイベントの実行を試行する」からの意図的な逸脱である。この PR で契約を定める際、同ドキュメントにも「順序依存の Operation 列を持つリコンサイラでは失敗時の打ち切りを許容する」旨の例外を追記する。

[#pr6]
=== PR 6: ローカルバックアップ準備とスナップショット作成のドメイン化

内容::
+
--
* `reconcileLocalBackup` のうち、ラベル（cluster-id / local-backup-target-pvc-uid）と finalizer の付与、`getSnapshotTarget` の判定部分（PVC UID 照合、`checkPVCBound`、PV からの image/pool 抽出）をドメイン化する。PVC・PV の取得はユースケース層が行いドメイン層へ渡す。
* `provisionRBDSnapshot` を「2 周のリコンサイル」に分解してドメイン化する。第 1 周はラベル・finalizer・PVC/PV マニフェスト（status）をメモリ上でセットして requeue（永続化はユースケース層）、第 2 周はこれらの永続化済みを確認してから `CreateAndFindRBDSnapshot` interface（この PR でドメイン層に定義、インフラ層で `ceph.CephCmd` により実装）でスナップショットを作成し、SnapID・CreatedAt・SnapSize・conditions をメモリ上で更新する。
* `Run` の永続化機構をこの PR で導入する（PR 3 から繰り延べられた分）。`Provision`/`Finalize` の呼び出し前に DeepCopy を取り、メタデータ・spec と status の dirty 判定を独立に行う。メタデータ・spec に差分がある場合だけ `Update`、status に差分がある場合だけ `Status().Update` を行い、両方に差分がある場合はこの順序で実行して更新後の resourceVersion を引き継ぐ。先行する永続化に失敗した場合は後続の永続化と Operations を実行しない。現行コードが競合対策として用いている再取得つき status 更新・`Patch` に相当する競合時の方針（conflict エラーを requeue に任せる、再取得してリトライする等）もこの PR で定める。
* 以上を standalone・primary の `Provision` の `if` として追記し、旧コードの該当部分を削除する。
--
テスト:: ラベル・finalizer 付与、マニフェスト未保存時の requeue、スナップショット作成後の status 更新、fake interface を使った作成失敗時の挙動。`Run` の永続化機構については、メタデータ・spec のみの変更では `Update` だけを呼ぶこと、status のみの変更では `Status().Update` だけを呼ぶこと、両方の変更では `Update` → `Status().Update` の順序で実行し resourceVersion を引き継ぐこと、先行する永続化が失敗したら後続の永続化と Operations を実行しないこと、finalizer 除去だけのパスで `Status().Update` を呼ばないこと。
注意点::
+
--
* **「永続化してから外部操作」の順序不変条件を壊さない。** `provisionRBDSnapshot` は「PVC/PV マニフェストを status に永続化した後に RBD スナップショットを作成する」ことでクラッシュ時の孤児スナップショットを防いでいる。同種の不変条件として「ラベル（local-backup-target-pvc-uid）・finalizer を永続化した後にスナップショットを作成する」もある。「変更をメモリ上に溜めて `Run` の最後に一括永続化」する標準パターンではこれが壊れるため、上記のとおり 2 周に分解する。外部から見た状態遷移の順序は変わらない。
* **`Run` に下請けヘルパを追加する際、legacy 委譲シグナルを取りこぼさない。** `reconcile.Result.ShouldReturn()` は legacy 委譲シグナルを見ないため、`if result.ShouldReturn() { return result }` だけで受けるとシグナルが「継続」として素通りし、`ToCtrlResult()` で「完了・エラーなし」に落ちてリコンサイルがサイレントに打ち切られる。legacy を伝播させるヘルパでは `ShouldContinueWithLegacyReconcile()` も併せて確認する。
* **legacy 委譲時に旧コードが古いオブジェクトを触らないようにする。** `Reconcile` と `usecase.Run` はそれぞれ独立に `MantleBackup` を取得している。この PR から `Run` が永続化を行うため、`Run` が更新後のオブジェクトを呼び出し元へ返すか、legacy 委譲時に `Reconcile` 側で再取得するかを決める。
* requeue が増える（許容例外）。2 周分解によりスナップショット作成までのリコンサイルが 1 周増える。また逐次 `if` の「処理を実行したら return する」構造により、従来 1 パス内で連続実行されていたサブフローの境界（スナップショット作成 → verify 開始など）でもそれぞれ 1 周増える。

内容:: `secondaryCleanup`（source backup の diff-to アノテーション削除、import Job・zero-out Job とその PVC/PV の削除、オブジェクトストレージ上のエクスポートデータ削除、中間スナップショット削除、verify リソース削除、対象 backup の diff-from・sync-mode アノテーション削除）と `finalizeSecondary` をドメイン化する。オブジェクトストレージ削除と中間スナップショット削除（一覧 → 判定 → 削除）はドメイン interface とする。削除するオブジェクト名は `spec.transferCompression` に依存する（<<d4>>）。オブジェクトストレージ削除は Provision の通常 cleanup（現行の `secondaryCleanup(ctx, backup, true)` 相当）でのみ同期的に実行し、全 part の削除成功を確認できた場合だけ対象 backup のアノテーション削除へ進む。削除に失敗した場合は対象 backup を変更せずエラーを返し、次回のリコンサイルで再試行する。Finalize（同 `false` 相当）ではオブジェクトストレージ削除を呼ばず、finalizer 除去をその成否に依存させない。K8s リソースの削除 Operation の発行、対象 backup 自身の変更、中間スナップショット削除は <<d9>> に従って別パスに分ける。Operation の型・実行器と interface のインフラ実装はこの PR で追加する。secondary の `Provision`（cleanup の `if`）と `Finalize` に追記し、旧コードを削除する。

注意点:: <<d9>> の順序不変条件を守る。複数パス分解により cleanup・finalize のリコンサイルが数周に増える（許容例外）。

[#target-structure]
== 目標構造

リファクタリング完了後の構成は次の通り。

ドメイン層（`internal/controller/domain`）::
ロールごとのドメインリコンサイラ `MBStandaloneReconciler`・`MBPrimaryReconciler`・`MBSecondaryReconciler` を定義する。それぞれが `Provision`・`Finalize` メソッドを持つ。standalone と primary が共有するローカルバックアップ処理は、ドメイン層内の共通関数（または両者に埋め込む共通構造体）として括り出す。リコンサイル対象の `MantleBackup` への変更はメモリ上で行い、それ以外の外部作用はドメインイベント（`domain.Operation`）として `ReconcilerOperations` に蓄積するか、ドメイン層で定義した narrow interface を介して行う（使い分けは <<d3>>）。

ユースケース層（`internal/controller/usecase`）::
ロールごとに `ReconcileMBStandalone`・`ReconcileMBPrimary`・`ReconcileMBSecondary` を定義する。それぞれの `Run` は「リコンサイル対象と管理対象判定に必要なリソースの取得 → <<managed-backup-preflight,管理対象の事前判定>> → その他の必要リソースの取得 → `DeletionTimestamp` による `Provision`/`Finalize` の呼び分け → 変更された `MantleBackup` の永続化 → Operations のインフラ層への引き渡し」を行う。

インフラ層（`internal/controller/infra` ほか）::
`infra.KubernetesClient.ApplyReconcilerOperations` に MantleBackup 用の Operation の実行を追加する。Ceph 操作は既存の `ceph.CephCmd`（インターフェース＋gomock 生成済み）、オブジェクトストレージ操作は既存の `objectstorage.Bucket`（インターフェース＋モックあり）、gRPC 操作は `proto.MantleServiceClient` をそれぞれ実装として利用する。`mantlebackup_controller.go` は最終的に、struct 定義・`SetupWithManager`（`WatchesRawSource` の配線を含む）・ロールに応じてユースケース層の `Run` を呼ぶだけの薄い `Reconcile`・ユースケース層の初期化のみになる。

[#design-decisions]
== 設計判断

[#d1]
=== D1: リコンサイル結果（requeue）の表現

ドメイン層の `Provision`・`Finalize` およびその下請け関数は、既存の `*reconcile.Result` をそのまま戻り値として使う。ドメイン層は優先度待ちの `reconcile.SlowRequeue()` も返す。ユースケース層の `Run` は `*reconcile.Result` を返し、インフラ層（`Reconcile`）で `ToCtrlResult()` により `ctrl.Result` へ変換する。

.この判断の根拠
[%collapsible]
====
* MBC PoC のドメイン層は plain `error` を返すが、MB では「成功として終了」「requeue」「slow requeue」「エラー」の四値の表現が必須（`expire` の要求経路、`checkPVCBound` の pending 待ち、優先度待ちの slow requeue など）。
* `internal/controller/internal/reconcile` は他の層に依存しない小さなユーティリティであり、ドメイン層から依存しても「ドメイン層は他のどの層にもコード上の依存がない」という制約には反しない。PoC のドメイン層も controller-runtime（`controllerutil`）に依存している前例がある。
* 既存サブフローの戻り値型と一致するため、移行時の書き換え量を最小化できる。
====

[#d2]
=== D2: 共有定数・純粋ヘルパの移動

MB-C のラベル・アノテーション・sync-mode・名前プレフィックス定数（優先度機能の `LabelBackupPriority`・`labelBackupPriorityHigh`、転送圧縮の `transferCompressionZstd` を含む）と、`Make*Name`・`ExtractPartNumFrom*` などの純粋ヘルパ関数は、それらを使用するコンポーネントをドメイン層へ移す PR で、コンポーネントと一緒にドメイン層（`internal/controller/domain`）へ移動する。定数・純粋ヘルパだけを先行して一括移動する PR は設けない。複数のコンポーネントから参照されるものは、それを最初に必要とするコンポーネントの移動 PR で移し、後続のコンポーネントは移動済みの定義を利用する。

移動に伴い機械的な参照先修正が必要な参照者は、`replication.go`・他コントローラ・既存テストのほかに **`cmd/backup`** がある（`LabelBackupPriority`・`MantleBackupConfigUID` を参照する。`MantleBackupConfigUID` は `cmd/backup/main.go` に同じ文字列の定義が重複しているので、移動を機に一本化してよい）。値は変えない（<<dod>>）。

`getCephClusterIDFromPVC`（`util.go`）は外部アクセス（StorageClass の読み取り）を持つためドメイン層へは移動せず、インフラ層へ移動する（<<d6>>）。

.この判断の根拠
[%collapsible]
====
* 定数・純粋ヘルパは「Mantle がどのように振る舞うか」の定義そのものであり、ドメイン層の管轄である。
* 一括移動 PR を設けないのは、レビュー時に利用側と定義を突き合わせて確認できるようにするため。
====

[#d3]
=== D3: Operations とインターフェースの使い分け

書き込み系はドメインイベント（Operation）を優先し、呼び出し結果がその場のリコンサイル判定に影響するものだけドメイン層定義の narrow interface を使う。読み取り系は原則ユースケース層が事前に取得してドメイン層へデータとして渡す。判断に迷ったら「呼び出し結果がその場の判定・出力に使われるか、またはリコンサイルパスをまたいで保持すべき状態か」を基準にする。分類は次の通り。

[cols="3,2,3", options="header"]
|===
| 外部アクセス | 方式 | 備考

| リコンサイル対象 `MantleBackup` の変更（ラベル・finalizer・アノテーション・status・conditions）
| メモリ上で変更し、ユースケース層が永続化
| 元のオブジェクトとの比較はメタデータ・spec と status で独立に行い、差分がある側だけ `Update` / `Status().Update` を呼ぶ。両方に差分がある場合は `Update` を先に行い、その応答の resourceVersion を使って `Status().Update` を行う。先行する永続化に失敗した場合は後続の永続化と Operation 適用を行わない（PR 6）

| Job・Pod・PVC・PV の作成／削除、他の `MantleBackup` の更新（diff-from アノテーションなど）、期限切れ backup の削除
| Operation
| Job マニフェスト構築はインフラ層に置く（<<d4>>）

| gRPC `CreateOrUpdatePVC` → `CreateMantleBackup`（レプリケーション）
| 複合 Operation
| 前者のレスポンス（PVC UID）を後者のリクエストが使うが、レスポンスをドメイン層の判定には使わないため、2 呼び出しをまとめた 1 つの Operation としてインフラ層で実行する（PR 10）

| gRPC `SetSynchronizing`
| Operation
| 同一パス内の後続処理はレスポンスに依存しない

| gRPC `ListMantleBackup`（セカンダリの backup 一覧）
| ユースケース層で事前取得
| 無条件取得にすると同期済み backup や先行 backup の同期待ち中にも gRPC 呼び出しが増えるため、段階的に事前取得する。まず primary の backup 一覧を K8s から取得し、ドメイン層の純粋関数で先行する全 backup が同期済みか判定する。対象が未同期かつ先行 backup がすべて同期済みの場合だけ `ListMantleBackup` を呼ぶ

| Job の完了状態・ラベル付き Job/PVC の一覧・対象 PVC の存在
| ユースケース層で事前取得
| `checkJobStatus`・`handleCompletedJobsOfComponent`・`canNewJobBeCreated`・`canNewExportDataPVCBeCreated` 相当の判定はドメイン層で行い、入力（Job/PVC のリスト・状態）はデータとして渡す。`deletePodsOfJob` 内の一覧取得は、不要な DeleteCollection を避けるための Operation 実行時の詳細としてインフラ層に置く

| オブジェクトストレージ `Exists`（secondary でのアップロード済み確認）・`GetSize`（primary のメトリクス）
| ユースケース層で事前取得
| 必要な状態のときだけ取得し、要否はドメイン層の判定関数で決める。primary の `GetSize` はメトリクス算出専用でリコンサイル判定には使わないため、クライアント初期化または `GetSize` に失敗してもエラーを返さず、ログを出してメトリクス更新だけをスキップし、verify・レプリケーション・cleanup を継続する

| オブジェクトストレージ `Delete`（secondary cleanup）
| ドメイン層定義の interface
| 削除の成功が対象 backup のアノテーション更新へ進む条件になるため Operation にはしない。Provision の通常 cleanup でのみ同期的に実行し、全 part の削除が成功した場合だけ後続へ進む。失敗時は対象 backup を変更せず、次回のリコンサイルで再試行する（<<d9>>）

| MantleBackupConfig の優先度ラベルの同期（`syncPriorityLabelFromMBC`）
| メモリ上で変更し、ユースケース層が永続化
| リコンサイル対象自身のラベル変更なので上記 1 行目と同じ扱いにする（現行の `Patch` は廃止する）。MantleBackupConfig の取得はユースケース層で事前取得し、取得の要否（`MantleBackupConfigUID` ラベルの有無）はドメイン層の純粋関数で決める（PR 12）

| 高優先度 backup の待ち判定（`shouldWaitForHigherPriorityBackup`・`shouldWaitForHigherPriorityImport`）
| ユースケース層で事前取得
| 高優先度 backup の一覧（削除中を除く）と、対象 backup が export-data PVC を保有しているかの入力となるラベル付き PVC 一覧をユースケース層が取得し、待つべきかの判定はドメイン層の純粋関数で行う。いずれも K8s のキャッシュ読み取りなので事前取得してよい。判定が真のときドメイン層は slow requeue を返す（PR 12・14）

| RBD スナップショットの作成（作成結果の ID・サイズ・タイムスタンプを status に書く）
| ドメイン層定義の interface
| 呼び出し結果がリコンサイル内容を決めるため。`CreateAndFindRBDSnapshot` のような専用 interface をドメイン層に定義し、インフラ層が `ceph.CephCmd` で実装する

| RBD スナップショットの削除（存在確認 → 削除 → 削除確認、`removeRBDSnapshot`）
| ドメイン層定義の interface
| 読み取り結果で分岐する一連の処理のため

| verify 用 clone イメージの作成（既存クローンと親スナップショットの確認 → 作成）
| ドメイン層定義の interface
| 読み取り結果で分岐する一連の処理のため。インフラ実装は `createCloneByPV` を利用する（<<d6>>）

| インポート済み RBD スナップショットの検索（`markSecondarySnapshotCaptured`）
| ドメイン層定義の interface
| 検索結果（SnapID）を status に書くため

| RBD ボリュームロック（`lockVolume`/`unlockVolume`）
| ドメイン層定義の interface
| ロックは複数リコンサイルパスにわたって保持される（Job 未完了の間は unlock せず requeue し、次パスでは取得済みの自ロックを確認して続行する）ため、Operation では表現できない

| 中間スナップショット削除・verify 用イメージ削除（Ceph）
| ドメイン層定義の interface
| 一覧取得 → 判定 → 削除の複合処理のため
|===

事前取得を条件付きで行う場合、その要否判定は**ドメイン層の純粋な判定関数**として定義し、ユースケース層はそれを呼び出すだけにする。判定に追加データが必要な場合は段階的に取得する。例えば `ListMantleBackup` の要否は `NeedsSecondaryBackupList(backup, primaryBackups)` のように primary の backup 一覧も入力とし、先行 backup の同期確認に合格した後だけ gRPC を呼ぶ。判定関数のためのデータを得る目的で、より高コストな外部アクセスを先に実行してはならない。

interface は「その処理に必要なメソッドのみ」を定義し、他の処理と共有しない。テストでは gomock（`ceph_mock.go` 相当）ではなく、必要に応じてテスト内で小さな fake を書く。

[#d4]
=== D4: Job マニフェスト構築の置き場所

`createOrUpdateExportJob`・`createOrUpdateUploadJobs`・`createOrUpdateImportJob`・`createOrUpdateZeroOutJob`・`createOrUpdateVerifyJob` の Job spec 構築コードは**インフラ層**に置く。

* ドメイン層が発行する Operation（例：`CreateOrUpdateExportJobOperation`）には、判定に由来するパラメータ（Job 名、対象 backup の情報、pool/image/snapshot 名、part 番号、full/incremental、転送サイズ、転送圧縮の形式など）のみを持たせる。
* Pod spec の詳細（コンテナ定義、env、securityContext、スクリプト、proxy 設定、`podImage`・`envSecret`、Job の affinity）はインフラ層の Operation 実行器が組み立てる。affinity は `PrimarySettings`・`SecondarySettings` 由来なので、Operation 実行器がこれらの設定を保持する（`podImage`・`envSecret`・`proxySettings`・`ExportDataStorageClass` と同じ扱い）。affinity は Operation のパラメータにしない。export/upload/import Job にのみ affinity が設定され、zero-out Job と verify Job には設定されないという非対称性はそのまま維持する。
* 一方、転送圧縮の形式（`spec.transferCompression`）は Job spec の詳細に閉じない。`MakeObjectNameOfExportedData` を通じてオブジェクトストレージ上のオブジェクト名（`zstd` 指定時は `.zst` サフィックス）を決めるため、Job 作成の Operation に加えて `GetSize`（PR 7・12 のメトリクス）・`Exists`（PR 14 の part 0 アップロード確認）・`Delete`（PR 15 のエクスポートデータ削除）でも層をまたいで渡す。

.この判断の根拠
[%collapsible]
====
* Pod spec の詳細は外部システム（Kubernetes）への依存の詳細である。PoC の `CreateOrUpdateMBCCronJobOperation` → `createOrUpdateMBCCronJob` と同じ関係になる。
* これによりドメイン層のユニットテストは「どの Job をどのパラメータで作ろうとしたか」の検証に集中でき、Job spec の細部はインテグレーション・E2E テスト（既存）に委ねられる。
====

[#d5]
=== D5: その他の配置

`exportedDiffSizeCache`::
メトリクス算出用のメモリ内キャッシュであり、リコンサイルの判定には使われない。primary のユースケース層（`ReconcileMBPrimary` のフィールド）に置く。キャッシュを参照して未取得 part の範囲を決める処理、各 part の `GetSize`、合計値の算出、全 part の取得に成功した後のキャッシュ更新は、可変状態を所有するユースケース層が一続きで行う。ドメイン層は受け取った合計値をメトリクスへ設定するだけとする。途中の part で `GetSize` が失敗した場合はキャッシュを更新しない。

`expireQueueCh`・`scheduleExpire`::
workqueue への遅延投入はインフラ層の関心。ドメイン層は「まだ期限切れでない」ことを判定して `ScheduleExpireOperation` を発行し、インフラ層の実行器がチャネルへ送出する。`SetupWithManager` の `WatchesRawSource` 配線は `mantlebackup_controller.go` に残す。

`prepareObjectStorageClient`（S3 クライアントの遅延初期化）::
インフラ層に移す。ConfigMap/Secret から認証情報を読んで `objectstorage.Bucket` を返す処理をインフラ層のコンポーネントとし、ユースケース層はそれを介して `Exists`/`GetSize` の事前取得を行う。ユースケース層からの利用は、PoC の `usecase.KubernetesClient` と同様にユースケース層で定義したインターフェースをインフラ層が実装する形（依存性逆転）とする。このコンポーネントは PR 7 で導入し、PR 12 の upload メトリクスと PR 14 の secondary `Exists` はそれを利用する。secondary の `Run` は<<managed-backup-preflight,管理対象の事前判定>>を通過した直後かつ `Provision`/`Finalize` の呼び出しより前にクライアントを初期化し、失敗した場合はそのリコンサイル全体を中断する（現行のエラー経路を変えないため）。primary ではクライアント初期化と `GetSize` はメトリクス算出専用であり、失敗時は <<d3>> のとおりリコンサイルを中断しない。

メトリクス出力::
PoC（`MBCPrimaryReconciler.Provision`）と同様、ドメイン層から `metrics` パッケージを直接呼んでよい。`metrics` パッケージは外部システムへのアクセスを持たないため、層依存の制約には抵触しない。

ユースケース層の初期化::
`NewMantleBackupReconciler` の中でインフラ層の Kubernetes クライアントと 3 ロール分のユースケース層コンポーネントを即時初期化する。MBC PoC が `sync.Once` による遅延初期化を用いているのは、その初期化が API サーバへのアクセスを必要とするためであり、MB では不要である。今後ユースケース層の初期化が API サーバ依存の情報を必要とするようになった場合は、MBC と同様の遅延初期化へ切り替える。

=== 管理対象の事前判定

管理対象判定は `Provision`/`Finalize` 内の逐次 `if` ではなく、ユースケース層 `Run` の共通事前判定として実行する。管理対象外の backup に対してロール固有の外部アクセスを行わないようにするためである。

判定ロジック（`labelClusterID` の一致、ラベル未付与時の PVC の cluster ID 照合）はドメイン層の純粋な判定関数に置き、`Run` はその関数を呼ぶ。PVC と cluster ID は判定に必要な場合だけ `Run` が取得する。管理対象外なら `Run` は成功扱いで終了し、secondary の S3 クライアント初期化を含む後続の事前取得や `Provision`/`Finalize` は実行しない。管理対象なら、secondary は S3 クライアントを初期化してから `Provision`/`Finalize` を呼ぶ（<<d5>>）。

=== D6: 共有ヘルパのインフラ層への移動

`util.go` の `createCloneByPV`・`deleteRBDImageAsynchronously`・`getCephClusterIDFromPVC`（と下請けの `getCephClusterIDFromSCName`）は、**エクスポートした上でインフラ層（`internal/controller/infra`）へ移動**し、`internal/controller` 側（他コントローラ・`replication.go`・既存テスト）は infra を参照するように機械的に修正する。移動は<<pr-list>>の方針 4 に従い、それぞれを初めて必要とする PR で行う：`getCephClusterIDFromPVC` は PR 5、`createCloneByPV` は PR 7、`deleteRBDImageAsynchronously` は PR 8。ユースケース層からの利用（PR 5 の cluster ID 取得）は、<<d5>> のオブジェクトストレージクライアントと同様に依存性逆転とする。

.この判断の根拠
[%collapsible]
====
これらは外部アクセスを持つヘルパであり、MB のドメイン interface のインフラ実装（verify 用 clone 作成・verify イメージ削除）やユースケース層の事前取得（cluster ID）が同じ処理を必要とする。一方でこれらは `mantlerestore_controller.go`・`persistentvolume_controller.go`・`replication.go` とも共有されている。`internal/controller` パッケージは `usecase`・`infra` を import 済みのため、`usecase`・`infra` 側から `internal/controller` のシンボルを参照すると import 循環になり、そのままでは再利用できない。逆向き（`internal/controller` → `infra`）の依存は既存なので循環しない。
====

[#d7]
=== D7: verify とレプリケーションの並行進行（primary）

primary では検証とレプリケーションが並行に進行し、e2fsck の完了を待たずに export/upload が始まる。この挙動を維持するため、verify 全体を「`if 未verify { return verify 処理 }`」のような終端する 1 つの `if` にはせず、次の構造でドメイン化する。

```go
if 未verify かつ verify Job が存在しない {
    return verify リソースの作成  // clone 作成（interface）→ 静的 PV/PVC・verify Job の作成（Operation）→ requeue
}
if 未verify かつ verify Job が完了している {
    Verified condition をメモリ上で更新する  // return せず後続の if へ継続する
}
// 未verify かつ verify Job 実行中の場合は、どの if にも該当せず後続へ継続する

...（primary はここにレプリケーションの if 群）...

if 未verify または（primary で）未同期 {
    return requeue  // cleanup は verify・同期の完了後のみ実行する
}
return cleanup
```

verify Job の存在・完了状態はユースケース層が事前取得したデータで判定する（<<d3>>）。2 つ目の `if` が return しない「継続処理」であることは、expire（PR 5）やメトリクス出力と同様に逐次 `if` の例外として扱う。**cleanup の前の「未verify なら requeue」のガードは必須である**。これがないと、verify Job の実行中に cleanup が verify リソース（Job・PV/PVC・clone）を削除してしまう。

standalone・secondary では verify の後続はこのガードと cleanup のみである。

[#d8]
=== D8: export-data PVC 上限と完了 part のリソース解放

primary の `--max-export-data-pvcs` は、managed Ceph cluster の namespace に同時に存在できる export-data PVC 数を制限する。リファクタリング後も次の挙動を維持する。

* `MaxExportDataPVCs == 0` は無制限とする。上限が有効な場合、新しい part の PVC が既に存在すれば、全体の PVC 数が上限以上でも対応する export Job の作成・更新を続行する。PVC が存在しない場合だけ、同 namespace の `app.kubernetes.io/name=mantle` かつ `app.kubernetes.io/component=export-data` の PVC を数え、上限未満なら作成する。削除中の PVC も backing PV が領域を消費しうるため数に含める。
* upload Job が完了した part は、最新の完了 part を含めて export-data PVC を直ちに削除する。最新の完了 upload Job は進捗管理のため残す一方、その part の export Job・upload Job の Pod は削除し、pvc-protection によって PVC が Terminating のままスロットを占有し続けることを防ぐ。最新でない完了 Job は Job 自体の削除により Pod も削除される。
* **export-data PVC を 1 つでも保有している backup は、優先度ゲートで待たせない**（削除中の PVC も保有とみなす）。占有されたスロットはその backup 自身のリコンサイルが進まない限り解放されないため、待たせると高優先度の backup を含む全 backup が永久に進めなくなる。
* `MaxExportDataPVCs` は primary の設定としてユースケース層・ドメイン層へ渡す。対象 part の PVC、ラベル付き PVC 一覧、完了 Job の状態はユースケース層が事前取得し、作成可否と解放対象はドメイン層が判定する。PVC・Pod の削除は Operation とし、PVC の削除要求後に最新完了 part の Pod を削除する順序で発行する。Pod の一覧取得と DeleteCollection は Operation 実行器が一続きで行う。

1 つ目・2 つ目を崩すと、特に `MaxExportDataPVCs == 1` の multi-part backup で、前 part の PVC がスロットを占有して次 part の PVC を作れないデッドロックが発生する。3 つ目を崩すと、低優先度 backup がスロットを保持したまま高優先度 backup を待ち、その高優先度 backup はスロットの解放を待つという循環待ちが発生する。

[#d9]
=== D9: クリーンアップ・ファイナライズにおける外部作用と対象の永続化の順序

`primaryCleanup`・`secondaryCleanup`・`finalizeStandalone`・`finalizeSecondary` は「**他リソースへの外部作用を完了してから**、対象 backup 自身の変更を永続化する」順序に依存している。

* source backup の diff-to アノテーション削除は、対象 backup の diff-from アノテーション削除（の永続化）より前に行う。逆順にすると、間でクラッシュや Operation の失敗が起きた場合に diff-from が先に消え、以降のリコンサイルは source を特定できなくなる。source には diff-to が残り続け、`finalize*` は diff-to があると何もしないため、source の finalize が永久にブロックされる。
* finalizer の除去は、Job・PVC・PV と RBD スナップショットの削除がすべて完了した後に永続化する。逆順にすると、finalizer 除去の永続化と同時に MantleBackup が消滅するため、その後の削除 Operation が失敗・クラッシュした場合にリソースがオーファン化し、それを再試行するリコンサイルも存在しなくなる。

ユースケース層の `Run` の標準的な順序は「対象の永続化 → Operations の適用」なので、素朴に 1 パスでドメイン化するとこの順序が逆転する。そこで cleanup・finalize は次のように**複数パスに分解**する。

. 削除対象（source の diff-to アノテーション、cleanup 対象の Job・PVC・PV）が事前取得データ上に残っている間は、削除 Operation を発行して requeue し、対象 backup 自身は変更しない。
. それらがすべて消えたことを確認できたパスで、secondary の Provision cleanup ではオブジェクトストレージ上のエクスポートデータを interface で同期的に削除する。全 part の削除に成功した場合だけ、対象 backup 自身の変更（diff-from・sync-mode アノテーションの削除）へ進んで requeue する。削除に失敗した場合は対象を変更せずエラーを返す。Finalize ではオブジェクトストレージ削除を行わずに対象アノテーションを削除して requeue する。
. 対象 backup のアノテーション削除が永続化された次のパスで、中間スナップショット削除を interface で同期実行する（現行の「対象アノテーションの永続化 → 中間スナップショット削除」の順序を維持するため）。すでにアノテーションが削除済みの場合も同じパスから再開できる。
. 中間スナップショット削除の成功後、finalize では RBD スナップショット削除（interface・同期実行）・メトリクス削除・finalizer 除去を行う。このパスでは、対象の変更より先に完了していなければならない Operation を発行しない。

オブジェクトストレージ削除は Provision cleanup に限って `Delete` 呼び出しの成功をゲートにするだけであり、削除後の `Exists` など追加の S3 読み取りは行わない。
