= mantlebackup_controller.go 段階的リファクタリング計画

== 目的

link:new-architecture.adoc[Mantle（再）設計案]に従い、`internal/controller/mantlebackup_controller.go`（約 3,600 行、以下 MB-C）を三層アーキテクチャ（ドメイン層・ユースケース層・インフラ層）にリファクタリングする。このリファクタリングにより以下を達成する：

* 本体コードの関心を分離し、Kubernetes クラスタや Ceph クラスタといった外部リソースにアクセスする部分（インフラ層）と、コントローラが次に何を行うべきかを判定する部分（ドメイン層）を分けることで、コードの見通しをよくする。ドメイン層では、どのような状況でリコンサイラがどのように振る舞うのかを明示的に書く。
* ドメイン層に対して Arrange-Act-Assert を明示した（envtest を用いない）ユニットテストを書き、リコンサイラの振る舞いを担保する。
* 実装中は https://martinfowler.com/bliki/StranglerFigApplication.html[ストラングラーフィグパターン]を活用し、レビューしやすい単位に PR を分割して進める。各 PR は単体でマージしても外部から見た振る舞いや機能を損ねず、コンパイルが通る。その代わり、PR 単体では nop になるコード（後続 PR から使われるコード）を許容する。

MantleBackupConfig コントローラで実施済みの PoC（ https://github.com/cybozu-go/mantle/pull/244[PR #244] 他。`internal/controller/domain`・`usecase`・`infra` パッケージ）のパターンを正とし、同じディレクトリ・同じ流儀で実装する。

== 基準コミット

本計画は、コミット https://github.com/cybozu-go/mantle/commit/007511aaf8de2bd7db016241258b0aec8cb0ecb2[`007511a`] 時点のコードに基づいて作成した。本書中の関数名・行数・挙動に関する記述はすべてこのコミット時点のものである。**各 PR の作成時には、その時点の最新の `main` と基準コミットの差分を確認し、対象コードに変更があれば本計画をその時点の `main` に基づいて適宜修正した上で着手すること。**

== スコープ外

* インテグレーションテスト（envtest を用いるテスト）の追加・修正・削除。ただしシンボル移動に伴う機械的な参照先修正（import・シンボル名の変更）は許容する。
* E2E テストの追加・修正・削除。ただしシンボル移動に伴う機械的な参照先修正（import・シンボル名の変更）は許容する（`test/e2e/multik8s/testutil` が `Make*Name` 系などを参照しているため）。
* gRPC によって呼び出される処理（`replication.go` のサーバ側実装）の改善。ただし定数・共有ヘルパの移動（<<d6>> 参照）に伴う機械的な import 修正は許容する。
* 外部から見た振る舞いが変わるような実装。リソース名（Job/PVC/PV のプレフィックス）、ラベル・アノテーション、`.status` の遷移、メトリクス、`--max-export-data-pvcs` によるスロットリングなど外部から観測可能な挙動を変えない。ただし <<risk-requeue>> に列挙した requeue 回数・エラー経路・gRPC 再送信の変化は許容例外とする。
* `mantlerestore_controller.go`・`garbage_collector_runner.go` など他コントローラのリファクタリング。ただし共有ヘルパのインフラ層への移動（<<d6>> 参照）に伴う機械的な参照先修正（import・シンボル名の変更）は許容する。

== 現状の構造

`MantleBackupReconciler` は 3 つのロール（standalone / primary / secondary）で動作し、`Reconcile()` がロールごとの処理に分岐する。主なサブフローと外部アクセスは次の通り：

[cols="2,3,2", options="header"]
|===
| サブフロー | 主な関数 | 外部アクセス

| 管理対象判定
| `checkManagedBackup`
| K8s（PVC・StorageClass の読み取り）

| 期限切れ処理
| `expire`, `scheduleExpire`
| K8s（MantleBackup 削除）、`expireQueueCh` による遅延 requeue

| ローカルバックアップ
| `reconcileLocalBackup`, `getSnapshotTarget`, `provisionRBDSnapshot`, `createRBDSnapshot`
| K8s（PVC/PV 読み取り、status 更新）、Ceph（`rbd snap create` ほか）

| 検証（verify）
| `verify`, `createOrUpdateVerifyJob`, `createStaticPV(C)IfNotExists`, `checkJobStatus`
| K8s（Job/PV/PVC 作成・状態確認）、Ceph（clone 作成）

| レプリケーション（primary）
| `replicate`, `replicateManifests`, `prepareForDataSynchronization`, `startExportAndUpload`, `startExport`, `startUpload`, `createOrUpdateExportJob`, `createOrUpdateUploadJobs`, `handleCompleted{Export,Upload}Jobs`, `canNewExportDataPVCBeCreated`, `deleteExportDataPVC`, `deletePodsOfJob`
| gRPC（`CreateOrUpdatePVC`, `CreateMantleBackup`, `ListMantleBackup`, `SetSynchronizing`）、K8s（Job/PVC の作成・一覧・削除、Pod の一覧・削除）、オブジェクトストレージ（`GetSize`）

| インポート（secondary）
| `startImport`, `reconcileZeroOutJob`, `reconcileImportJob`, `createStaticPV(C)IfNotExists`, `lockVolume`/`unlockVolume`, `markSecondarySnapshotCaptured`
| K8s（Job/PV/PVC 作成）、Ceph（`rbd lock add/ls/rm`）、オブジェクトストレージ（`Exists`）

| クリーンアップ・ファイナライズ
| `primaryCleanup`, `secondaryCleanup`, `finalizeStandalone`, `finalizeSecondary`, `removeRBDSnapshot`, `deleteMiddleSnapshots`
| K8s（Job/PVC/PV 削除）、Ceph（`rbd snap rm` ほか）、オブジェクトストレージ（`Delete`）
|===

補足事項：

* 全サブフローは `internal/controller/internal/reconcile` パッケージの `*reconcile.Result`（succeeded / requeue / error の三値）を、単独または多値返却の一部（`getSnapshotTarget`・`checkJobStatus`・`lockVolume` など）として返す（workqueue に登録するハンドラ関数である `scheduleExpire` を除く）。
* MB-C の先頭で定義されているラベル・アノテーション・sync-mode などの定数は、スコープ外の `replication.go` からも参照されている（primary↔secondary 間のワイヤ契約）。
* `Make*Name`・`ExtractPartNumFrom*`・`searchForDiffOriginMantleBackup`・`calculateExportDataPVCSize` などの純粋関数が多数存在し、これらは MB-C とテスト（E2E の `testutil` を含む）以外から参照されていない。
* `exportedDiffSizeCache`（メトリクス用のメモリ内キャッシュ）と `expireQueueCh`（遅延 requeue 用チャネル）という 2 つの内部状態を持つ。このほか `objectStorageClient`（遅延初期化される S3 クライアント）も可変な内部状態である（<<d5>> 参照）。

== 目標構造

リファクタリング完了後の構成は次の通り。

ドメイン層（`internal/controller/domain`）::
ロールごとのドメインリコンサイラを定義する：
+
* `MBStandaloneReconciler`
* `MBPrimaryReconciler`
* `MBSecondaryReconciler`
+
それぞれが `Provision`・`Finalize` メソッドを持ち、new-architecture.adoc の指示通り「`if 条件 { return 処理 }` の逐次実行」スタイルで記述する。standalone と primary が共有するローカルバックアップ処理は、ドメイン層内の共通関数（または両者に埋め込む共通構造体）として括り出す。リコンサイル対象の `MantleBackup` への変更はメモリ上で行い、それ以外の外部作用はドメインイベント（`domain.Operation`）として `ReconcilerOperations` に蓄積するか、ドメイン層で定義した narrow interface を介して行う（使い分けは <<d3>> 参照）。

ユースケース層（`internal/controller/usecase`）::
ロールごとに `ReconcileMBStandalone`・`ReconcileMBPrimary`・`ReconcileMBSecondary` を定義し、それぞれの `Run` が「必要リソースの取得 → `DeletionTimestamp` による `Provision`/`Finalize` の呼び分け → 変更された `MantleBackup` の永続化 → Operations のインフラ層への引き渡し」を行う。PoC の `ReconcileMBCPrimary.Run` と同じ流儀。

インフラ層（`internal/controller/infra` ほか）::
`infra.KubernetesClient.ApplyReconcilerOperations` に MantleBackup 用の Operation の実行を追加する。Ceph 操作は既存の `ceph.CephCmd`（インターフェース＋gomock 生成済み）を、オブジェクトストレージ操作は既存の `objectstorage.Bucket`（インターフェース＋モックあり）を、gRPC 操作は `proto.MantleServiceClient` をそれぞれ実装として利用する。`mantlebackup_controller.go` は最終的に `SetupWithManager` と、ロールに応じてユースケース層の `Run` を呼ぶだけの薄い `Reconcile` のみになる。

== 主要な設計判断

[#d1]
=== D1: リコンサイル結果（requeue）の表現

ドメイン層の `Provision`・`Finalize` およびその下請け関数は、既存の `*reconcile.Result` をそのまま戻り値として使う。

* MBC PoC のドメイン層は plain `error` を返すが、MB では「成功として終了」「requeue」「エラー」の三値の表現が必須（`expire` の要求経路、`checkPVCBound` の pending 待ちなど）。
* `internal/controller/internal/reconcile` は他の層に依存しない小さなユーティリティであり、ドメイン層から依存しても new-architecture.adoc の「ドメイン層は他のどの層にもコード上の依存がない」という制約（層への依存の禁止）には反しない。PoC のドメイン層も controller-runtime（`controllerutil`）に依存している前例がある。
* 既存サブフローの戻り値型と一致するため、移行時の書き換え量を最小化できる。

ユースケース層の `Run` は `*reconcile.Result` を返し、インフラ層（`Reconcile`）で `ToCtrlResult()` により `ctrl.Result` へ変換する。

[#d2]
=== D2: 共有定数・純粋ヘルパの移動

MB-C 先頭のラベル・アノテーション・sync-mode・名前プレフィックス定数、および `Make*Name`・`ExtractPartNumFrom*` などの純粋ヘルパ関数は、ドメイン層（`internal/controller/domain`）に移動する。

* これらは「Mantle がどのように振る舞うか」の定義そのものであり、ドメイン層の管轄。
* `replication.go`・既存 envtest テストからの参照は import 変更のみの機械的修正で追従する（PR 2 で実施）。
* `getCephClusterIDFromPVC`（`util.go`）は外部アクセス（StorageClass の読み取り）を持つためドメイン層へは移動せず、インフラ層へ移動する（`mantlerestore_controller.go`・`replication.go` と共有しているため機械的な参照先修正を伴う。<<d6>> 参照）。

[#d3]
=== D3: Operations とインターフェースの使い分け

new-architecture.adoc の方針通り、**書き込み系はドメインイベント（Operation）を優先**し、**呼び出し結果がその場のリコンサイル判定に影響するものだけ**ドメイン層定義の narrow interface を使う。読み取り系は原則ユースケース層が事前に取得してドメイン層へデータとして渡す。分類は次の通り：

[cols="3,2,3", options="header"]
|===
| 外部アクセス | 方式 | 備考

| リコンサイル対象 `MantleBackup` の変更（ラベル・finalizer・アノテーション・status・conditions）
| メモリ上で変更し、ユースケース層が永続化
| PoC と同じ方式。ただし永続化はメタデータの `Update` と status の `Status().Update` の両方を行う（PoC は `Update` のみ）。<<risk-persist-order>> の例外あり

| Job・Pod・PVC・PV の作成／削除、他の `MantleBackup` の更新（diff-from アノテーションなど）、期限切れ backup の削除
| Operation
| Job マニフェスト構築はインフラ層に置く（<<d4>>）

| gRPC `CreateOrUpdatePVC` → `CreateMantleBackup`（レプリケーション）
| 複合 Operation
| 前者のレスポンス（PVC UID）を後者のリクエストが使うが、レスポンスをドメイン層の判定には使わないため、2 呼び出しをまとめた 1 つの Operation としてインフラ層で実行する。なお現行実装は送信直後の同一パス内で `ListMantleBackup` が送信結果を読むため、Operation 化に伴い 2 周のリコンサイルに分解する（PR 11・<<risk-requeue>> 参照）

| gRPC `SetSynchronizing`
| Operation
| 同一パス内の後続処理はレスポンスに依存しない

| gRPC `ListMantleBackup`（セカンダリの backup 一覧）
| ユースケース層で事前取得
| 無条件取得にすると同期済み backup のリコンサイルごとに gRPC 呼び出しが増えるため、取得の要否はドメイン層の判定関数で決める（後述）

| Job の完了状態・ラベル付き Job/PVC の一覧・対象 PVC の存在
| ユースケース層で事前取得
| `checkJobStatus`・`handleCompletedJobsOfComponent`・`canNewJobBeCreated`・`canNewExportDataPVCBeCreated` 相当の判定はドメイン層で行い、入力（Job/PVC のリスト・状態）はデータとして渡す。`deletePodsOfJob` 内の一覧取得は、不要な DeleteCollection を避けるための Operation 実行時の詳細としてインフラ層に置く

| オブジェクトストレージ `Exists`（secondary でのアップロード済み確認）・`GetSize`（primary のメトリクス）
| ユースケース層で事前取得
| 必要な状態のときだけ取得する。取得の要否はドメイン層の判定関数で決める（後述）

| RBD スナップショットの作成（作成結果の ID・サイズ・タイムスタンプを status に書く）
| ドメイン層定義の interface
| 呼び出し結果がリコンサイル内容を決めるため。`CreateAndFindRBDSnapshot` のような専用 interface をドメイン層に定義し、インフラ層が `ceph.CephCmd` で実装する

| RBD スナップショットの削除（存在確認 → 削除 → 削除確認、`removeRBDSnapshot`）
| ドメイン層定義の interface
| 読み取り結果で分岐する一連の処理のため

| verify 用 clone イメージの作成（既存クローンと親スナップショットの確認 → 作成）
| ドメイン層定義の interface
| 読み取り結果で分岐する一連の処理のため。インフラ実装は `createCloneByPV` を利用する（<<d6>>）

| インポート済み RBD スナップショットの検索（`markSecondarySnapshotCaptured`）
| ドメイン層定義の interface
| 検索結果（SnapID）を status に書くため

| RBD ボリュームロック（`lockVolume`/`unlockVolume`）
| ドメイン層定義の interface
| ロックは複数リコンサイルパスにわたって保持される（Job 未完了の間は unlock せず requeue し、次パスでは取得済みの自ロックを確認して続行する）ため、Operation では表現できない

| 中間スナップショット削除・verify 用イメージ削除（Ceph）
| ドメイン層定義の interface
| 一覧取得 → 判定 → 削除の複合処理のため
|===

事前取得を条件付きで行う場合（特に gRPC・S3・`rbd` コマンドの呼び出し回数を増やさないための条件）、その要否判定は**ドメイン層に純粋な判定関数**（例：`NeedsSecondaryBackupList(backup) bool`）として定義し、ユースケース層はそれを呼び出すだけにする。「どのような状況で何が必要か」はドメインロジックであり、ユースケース層に埋め込まない。判定関数として括り出すことでユニットテストの対象にもなる。

interface は new-architecture.adoc の指示通り「その処理に必要なメソッドのみ」を定義し、他の処理と共有しない。テストでは gomock（`ceph_mock.go` 相当）ではなく、必要に応じてテスト内で小さな fake を書く。

[#d4]
=== D4: Job マニフェスト構築の置き場所

`createOrUpdateExportJob`（約 180 行）・`createOrUpdateUploadJobs`・`createOrUpdateImportJob`（約 215 行）・`createOrUpdateZeroOutJob`・`createOrUpdateVerifyJob` の Job spec 構築コードは**インフラ層**に置く。

* ドメイン層が発行する Operation（例：`CreateOrUpdateExportJobOperation`）には、判定に由来するパラメータ（Job 名、対象 backup の情報、pool/image/snapshot 名、part 番号、full/incremental、転送サイズなど）のみを持たせる。
* Pod spec の詳細（コンテナ定義、env、securityContext、スクリプト、proxy 設定、`podImage`・`envSecret`）は外部システム（Kubernetes）への依存の詳細であり、インフラ層の Operation 実行器が組み立てる。PoC の `CreateOrUpdateMBCCronJobOperation` → `createOrUpdateMBCCronJob` と同じ関係。
* これによりドメイン層のユニットテストは「どの Job をどのパラメータで作ろうとしたか」の検証に集中でき、Job spec の細部はインテグレーション・E2E テスト（既存）に委ねる。

[#d5]
=== D5: その他の配置

`exportedDiffSizeCache`::
メトリクス算出用のメモリ内キャッシュであり、リコンサイルの判定には使われない。primary のユースケース層（`ReconcileMBPrimary` のフィールド）に置く。

`expireQueueCh`・`scheduleExpire`::
workqueue への遅延投入はインフラ層の関心。ドメイン層は「まだ期限切れでない」ことを判定して `ScheduleExpireOperation` を発行し、インフラ層の実行器がチャネルへ送出する。`SetupWithManager` の `WatchesRawSource` 配線は現状のまま `mantlebackup_controller.go` に残す。

`prepareObjectStorageClient`（S3 クライアントの遅延初期化）::
インフラ層に移す。ConfigMap/Secret から認証情報を読んで `objectstorage.Bucket` を返す処理をインフラ層のコンポーネントとし、ユースケース層はそれを介して `Exists`/`GetSize` の事前取得を行う。ユースケース層からの利用は、PoC の `usecase.KubernetesClient` と同様にユースケース層で定義したインターフェースをインフラ層が実装する形（依存性逆転）とし、new-architecture.adoc の「ユースケース層はインフラ層に依存しない」制約を守る。なおこのコンポーネントは primary（PR 13 の `GetSize`。現行の `setExportedDiffSizeMetric` も `prepareObjectStorageClient` を呼んでいる）と secondary（PR 15 の `Exists`）の双方で必要になるため、PR 13・15 のうち先にマージされる方の PR で導入し、後の PR はそれを利用する。また現行の secondary は毎リコンサイルの冒頭（所有権スキップ判定より前）でクライアントを初期化し、失敗した場合はそのリコンサイル全体を中断する。このエラー経路を変えないため、新実装でも secondary の `Run` は冒頭で（`Exists` の要否に関わらず）クライアントの初期化を行う。

メトリクス出力::
PoC（`MBCPrimaryReconciler.Provision`）と同様、ドメイン層から `metrics` パッケージを直接呼んでよい。`metrics` パッケージは外部システムへのアクセスを持たないため、new-architecture.adoc の層依存の制約には抵触しない。

ユースケース層の初期化::
MBC PoC と同様、`MantleBackupReconciler.Reconcile` 内で `sync.Once` により遅延初期化する（既存 envtest スイートの制約。PoC の TODO コメント参照）。

[#d6]
=== D6: 共有ヘルパのインフラ層への移動

`util.go` の `createCloneByPV`・`deleteRBDImageAsynchronously`・`getCephClusterIDFromPVC`（と下請けの `getCephClusterIDFromSCName`）は外部アクセスを持つヘルパであり、MB のドメイン interface のインフラ実装（verify 用 clone 作成・verify イメージ削除）やユースケース層の事前取得（cluster ID）が同じ処理を必要とする。一方でこれらは `mantlerestore_controller.go`・`persistentvolume_controller.go`・`replication.go` とも共有されている。`internal/controller` パッケージは `usecase`・`infra` を import 済みのため、`usecase`・`infra` 側から `internal/controller` のシンボルを参照すると import 循環になり、そのままでは再利用できない。

そこで、これらのヘルパは**エクスポートした上でインフラ層（`internal/controller/infra`）へ移動**し、`internal/controller` 側（他コントローラ・`replication.go`・既存テスト）は infra を参照するように機械的に修正する（`internal/controller` → `infra` の依存は既存のため循環しない）。移動は<<migration-strategy-note,移行戦略>>の方針 4 に従い、それぞれを初めて必要とする PR で行う：`getCephClusterIDFromPVC` は PR 6、`createCloneByPV` は PR 8、`deleteRBDImageAsynchronously` は PR 9。ユースケース層からの利用（PR 6 の cluster ID 取得）は、<<d5>> のオブジェクトストレージクライアントと同様に、ユースケース層で定義したインターフェースをインフラ層が実装する形（依存性逆転）とする。

[#d7]
=== D7: verify とレプリケーションの並行進行（primary）

現行の primary は、verify Job が未完了でも同一リコンサイルパス内でレプリケーション処理へ進む（`verify` は Job 未完了時に requeue ではなく「継続」を返す）。つまり検証とレプリケーションは並行に進行し、e2fsck の完了を待たずに export/upload が始まる。verify 全体を「`if 未verify { return verify 処理 }`」のような終端する 1 つの `if` にするとレプリケーション開始が検証完了まで遅延してしまうため、この形は採らず、verify を次の構造でドメイン化する：

```go
if 未verify かつ verify Job が存在しない {
    return verify リソースの作成  // clone 作成（interface）→ 静的 PV/PVC・verify Job の作成（Operation）→ requeue
}
if 未verify かつ verify Job が完了している {
    Verified condition をメモリ上で更新する  // return せず後続の if へ継続する
}
// 未verify かつ verify Job 実行中の場合は、どの if にも該当せず後続へ継続する

...（primary はここにレプリケーションの if 群）...

if 未verify または（primary で）未同期 {
    return requeue  // cleanup は verify・同期の完了後のみ実行する（現行の挙動と同じ）
}
return cleanup
```

verify Job の存在・完了状態はユースケース層が事前取得したデータで判定する（<<d3>>）。2 つ目の `if` が return しない「継続処理」であることは、expire（PR 6）やメトリクス出力と同様に new-architecture.adoc が許容する逐次 `if` の例外として扱う。cleanup の前の「未verify なら requeue」のガードは、verify Job の実行中に cleanup が verify リソース（Job・PV/PVC・clone）を削除してしまうことを防ぐために必須である。この構造により：

* primary では verify Job の実行中・完了のパスでも後続のレプリケーションの `if` に到達し、現行どおり検証とレプリケーションが並行進行する。standalone・secondary では verify の後続はガードと cleanup のみである。
* verify リソース作成の `if` は return するため、現行（作成と同一パスでレプリケーションも進む）に比べ検証開始パスでリコンサイルが 1 周増える（<<risk-requeue>> の許容例外）。
* 現行は未 verify の間、毎パスで clone・静的 PV/PVC・Job を再確認・再作成していた（`rbd ls` も毎パス発行される）が、新実装では verify Job が存在しない場合のみ作成する。Ceph への呼び出しが減る方向の変化であり許容する。
* 完了パスでは condition をメモリ上で更新して継続するため、verify 完了後の余分な 1 周が消える（<<risk-requeue>> 参照）。

=== D8: export-data PVC 上限と完了 part のリソース解放

primary の `--max-export-data-pvcs` は、managed Ceph cluster の namespace に同時に存在できる export-data PVC 数を制限する。リファクタリング後も次の挙動を維持する：

* `MaxExportDataPVCs == 0` は無制限とする。上限が有効な場合、新しい part の PVC が既に存在すれば、全体の PVC 数が上限以上でも対応する export Job の作成・更新を続行する。PVC が存在しない場合だけ、同 namespace の `app.kubernetes.io/name=mantle` かつ `app.kubernetes.io/component=export-data` の PVC を数え、上限未満なら作成する。削除中の PVC も backing PV が領域を消費しうるため数に含める。
* upload Job が完了した part は、最新の完了 part を含めて export-data PVC を直ちに削除する。最新の完了 upload Job は進捗管理のため残す一方、その part の export Job・upload Job の Pod は削除し、pvc-protection によって PVC が Terminating のままスロットを占有し続けることを防ぐ。最新でない完了 Job は従来どおり Job 自体の削除により Pod も削除される。
* `MaxExportDataPVCs` は primary の設定としてユースケース層・ドメイン層へ渡す。対象 part の PVC、ラベル付き PVC 一覧、完了 Job の状態はユースケース層が事前取得し、作成可否と解放対象はドメイン層が判定する。PVC・Pod の削除は Operation とし、現行どおり PVC の削除要求後に最新完了 part の Pod を削除する順序で発行する。Pod の一覧取得と DeleteCollection は Operation 実行器が一続きで行う。

この挙動を崩すと、特に `MaxExportDataPVCs == 1` の multi-part backup で、前 part の PVC がスロットを占有して次 part の PVC を作れないデッドロックが発生する。PR 12・13 では既存の envtest・E2E テストに加え、ドメイン層のユニットテストでこの不変条件を担保する。

== 段階的移行計画

[#migration-strategy-note]
=== 移行戦略

ストラングラーフィグパターンに基づき、次の方針で進める：

1. **最初に最終形と同じ呼び出し経路（`Reconcile` → `usecase.Run` → `domain.Provision`/`Finalize`）を骨組みとして導入する**（PR 3 で何もしないスケルトンと呼び出し経路を、PR 4 で legacy 委譲の仕組みを導入する）。ドメイン層の関数を旧コードから直接呼ぶ中間状態は作らず、ドメイン化された処理は常にユースケース層経由で実行される。
2. 移行が完了していない状況に対しては、`Provision`/`Finalize` が「旧コードに委譲する」ことを表す一時的な戻り値（以下 **legacy 委譲シグナル**）を返す。`Run` は、そこまでにドメイン層が行ったリコンサイル対象の変更の永続化と Operations の適用を済ませた上でシグナルを呼び出し元へ伝え、`Reconcile` が旧コード経路を実行する。
3. サブフローを 1 つずつドメイン化し、`Provision`/`Finalize` の逐次 `if` に追記していく。ドメイン化したサブフローの旧コードは同じ PR で削除する。あるロールの全サブフローが揃ったら、そのロールの legacy 委譲シグナルと旧コード経路を削除する。従来方式のような「一括切り替え PR」は不要になり、ロール完成時の PR は削除が主体の低リスクなものになる。
4. Operation 型・インフラ層の Operation 実行器・ドメイン interface のインフラ実装は、先行 PR でまとめて導入せず、**それらを初めて使用する PR で一緒に追加する**。レビュー時に発行側（ドメイン層）と実行側（インフラ層）を突き合わせて確認できるようにするためでもある。
5. ロールは standalone → primary → secondary の順に完成させる。standalone のフローは primary の部分集合（ローカルバックアップ＋verify＋cleanup）なので、共有部分のドメイン化がそのまま primary の下準備になる。

「最初からユースケース層経由」での移行が可能な理由と、そのために必要な一時的な仕組みは次の通り：

* `Provision`/`Finalize` は「`if 条件 { return 処理 }` の逐次実行」であり、原則として 1 回のリコンサイルは最初に成立した条件の処理だけを実行して終わる（expire や verify の condition 更新のような、処理をしても return しない「継続処理」の例外はある。PR 6・<<d7>> 参照）。そのため「移行済みの条件の `if`」と「未移行の状況で legacy 委譲シグナルを返す `if`」が同じ関数内に矛盾なく共存でき、サブフローをフロー順に縛られることなく 1 つずつ移行できる。
* legacy 委譲シグナルはドメイン層に定義する一時的な戻り値であり、全ロールの移行完了時（PR 17）に仕組みごと削除する。
* 例外として、primary でリコンサイルごとに実行されるメトリクス復元処理（`setExportedDiffSizeMetric` 系。現状はローカルバックアップ処理と deletionTimestamp 確認の後で毎回実行される）は「条件で終端する処理」ではないため逐次 `if` に馴染まない。移行（PR 13）までは `Reconcile` の primary 分岐（`usecase.Run` 呼び出しの前）へ巻き上げて残す。巻き上げの際、削除中（deletionTimestamp 付き）の backup では実行しないガードを添える（`finalizeStandalone` によるメトリクス削除後の再設定を防ぐため）。

この戦略により、どの時点でも未移行の経路は旧コードが現役で動き続け、各 PR のレビュー範囲が「1 サブフローのドメイン化とそのテスト」に限定される。

==== PR 3: ドメイン層・ユースケース層のスケルトン導入

* **内容**: 3 ロール分のドメインリコンサイラ（`MBStandaloneReconciler`・`MBPrimaryReconciler`・`MBSecondaryReconciler`）の空の `Provision`/`Finalize` と、ユースケース層の `ReconcileMB{Standalone,Primary,Secondary}`（何もしない `Run`）をスケルトンとして追加し、`Reconcile` の各ロール分岐の冒頭から `usecase.Run` を呼び出すように配線する。この時点の `Run`・`Provision`・`Finalize` は何もせずに即座に戻り、`Reconcile` はその後も従来の旧コード経路をそのまま実行するため、外部挙動は変わらない。ユースケース層の遅延初期化（`sync.Once`。<<d5>> 参照）もこの PR で行う。
* **nop**: `Run`・`Provision`/`Finalize` は何も処理しない（呼び出されるが nop）。
* **テスト**: 不要（検証すべき振る舞いがないため）。コンパイルと既存テストの通過のみ確認する。
* **規模**: 小。最終形と同じ呼び出し経路（`Reconcile` → `usecase.Run` → `domain.Provision`/`Finalize`）の骨格を最初に確立する PR。

==== PR 4: legacy 委譲シグナルと Run の骨組みの実装

* **内容**: PR 3 のスケルトンに骨組みの実装を入れる。legacy 委譲シグナル（ドメイン層に定義する一時的な戻り値）を導入し、この時点の `Provision`/`Finalize` はそれを返すだけとする。`Run` には「必要リソースの取得 → `DeletionTimestamp` による `Provision`/`Finalize` の呼び分け → 変更された `MantleBackup` の永続化 → Operations のインフラ層への引き渡し → legacy 委譲シグナルの伝播」の骨組みを実装し、`Reconcile` はシグナルを受けた場合に旧コード経路へ委譲するようにする。`Provision`/`Finalize` は legacy 委譲シグナルを返すだけなので、外部挙動は変わらない。`Run` の永続化は、MantleBackup がメタデータ（ラベル・finalizer・アノテーション）と status の両方を変更対象とするため、`Update` と `Status().Update` の両方を行う（PoC の `Run` は `Update` のみ）。現行コードが競合対策として用いている再取得つき status 更新・`Patch` に相当する競合時の方針（conflict エラーを requeue に任せる、再取得してリトライする等）もこの PR で定める。
* **nop**: `Provision`/`Finalize` は何も処理しないため、`Run` の骨組み以外は実質 nop。
* **テスト**: `Run` の骨組み（`DeletionTimestamp` による呼び分け・変更の永続化・Operations の適用・legacy 委譲シグナルの伝播）に対する AAA ユニットテスト。
* **規模**: 小〜中。
* **備考**: Operation 型・`infra.ApplyReconcilerOperations` の実行器・ドメイン interface のインフラ実装は、この PR ではまとめて導入せず、それらを初めて使用する後続 PR で一緒に追加する（<<migration-strategy-note,移行戦略>> の方針 4）。そのため、この PR 時点では MB 用の Operation 型と適用契約は存在しない。`Run` の「Operations の引き渡し」は PoC 由来の汎用機構（`domain.Operation`・`domain.ReconcilerOperations`）とユースケース層定義の適用インターフェースに対して実装し、この PR のユニットテストは fake の Operation・適用先で行う（MB 用実行器と打ち切り契約は PR 6 で導入・決定する。<<risk-op-order>>）。

==== PR 5: 所有権ガードのドメイン化

* **内容**: `isCreatedWhenMantleControllerWasSecondary` による所有権スキップ判定（standalone・primary ではリモートの mantle-controller が作成した backup を、secondary では自身が secondary として作成したのでない backup を、データ喪失防止のためスキップして成功扱いにする）をドメイン化し、全ロールの `Provision`/`Finalize` の冒頭の `if` として追記する。旧コードの該当分岐（`reconcileLocalBackup` 冒頭・`reconcileAsSecondary` 冒頭）は削除する。外部アクセスを伴わない純粋な判定のみのため、Operation・interface は導入しない。
* **テスト**: ロールごとにスキップ条件の向きが逆になることの AAA ユニットテスト。
* **規模**: 小。最初のサブフロー移行 PR。
* **備考**: expire（PR 6）より前に必ず本 PR を完了させること。所有権ガードが旧コード側に残ったまま expire をドメイン層の `Provision` に置くと、本来スキップすべき backup（例：primary 上のリモート作成 backup）をドメイン層の expire が削除しうるため（<<risk-legacy>> 参照）。

==== PR 6: expire と checkManagedBackup のドメイン化

* **内容**: `expire` の判定ロジック（CreatedAt 未設定・deletionTimestamp・retain-if-expired アノテーション・期限計算）をドメイン化し、削除は `DeleteMantleBackupOperation`、遅延 requeue は `ScheduleExpireOperation` として発行する。`checkManagedBackup` の判定部分（ラベル一致・cluster ID 照合）もドメイン化し、PVC と cluster ID の取得はユースケース層（`Run`）が行いドメイン層へ渡す。cluster ID の取得はユースケース層定義のインターフェース経由とし、その実装としてインフラ層へ移動した `getCephClusterIDFromPVC` を用いる（<<d6>>。`mantlerestore_controller.go`・`replication.go`・既存テストの参照は機械的に修正する）。PVC の取得は従来通り labelClusterID 未付与の場合にのみ行い（要否はドメイン層の判定関数で決める）、NotFound はエラーとせずデータとしてドメイン層へ渡す（無条件取得＋NotFound を requeue にすると、PVC 削除済み backup の finalize が進まなくなるため）。追記位置は次の通り：checkManagedBackup の `if` は全ロールの `Provision`/`Finalize` の冒頭（所有権ガードより前）、expire の `if` は全ロールの `Provision` の所有権ガードの後。expire は deletionTimestamp が付いた backup では何もしないため、`Finalize` への追記は不要。旧 `expire`・`checkManagedBackup` は削除する。両 Operation の型とインフラ層の実行器（`expireQueueCh` の注入を含む）はこの PR で追加する。MB 用の Operation 適用は「発行順に実行し、失敗したら残りを打ち切る」契約とし、この PR で定める（<<risk-op-order>> 参照）。なお expire は、未失効の場合に `ScheduleExpireOperation` を発行した上で後続の `if` へ処理を続ける。これは「`if 条件 { return 処理 }`」の逐次実行に馴染まない継続処理だが、Operation の発行のみで判定には影響しないため、メトリクス出力と同様に new-architecture.adoc が許容する例外として扱う。
* **テスト**: 「期限切れなら削除 Operation を発行する」「retain-if-expired なら何もしない」「未期限なら schedule Operation を発行する」「PVC NotFound なら requeue する」等の AAA ユニットテスト。
* **規模**: 小〜中。Operation を用いる最初のサブフロー移行としてパターンを確立する PR。

==== PR 7: ローカルバックアップ準備とスナップショット作成のドメイン化

* **内容**:

* **テスト**: ラベル・finalizer 付与、マニフェスト未保存時の requeue、スナップショット作成後の status 更新、fake interface を使った作成失敗時の挙動。
* **規模**: 中。ドメイン interface を使う最初の PR。

==== PR 8: verify のドメイン化

* **内容**: `verify` を <<d7>> の構造（「verify Job が無ければ clone 作成（interface）・静的 PV/PVC・verify Job の作成（Operation）を行い requeue」「verify Job が完了していれば Verified condition をメモリ上で更新して後続へ継続」、cleanup 前の「未verify なら requeue」ガード）に書き換える。verify Job の存在・完了状態はユースケース層が `checkJobStatus` 相当で取得してデータとして渡す。clone 作成 interface のインフラ実装（`createCloneByPV` のインフラ層への移動を含む。<<d6>>）と各 Operation の型・実行器（`createOrUpdateVerifyJob` の Job spec 構築、`createStaticPV(C)IfNotExists` の本体を含む）はこの PR で追加する。全ロールの `Provision` の該当 `if` として追記し、旧 `verify` 系コードを削除する。とくに primary では verify Job の実行中・完了パスでレプリケーション（PR 13 までは legacy 委譲経由の旧コード）へ処理が継続し、検証とレプリケーションが従来どおり並行進行することを、削除した旧コードの分岐条件と突き合わせて確認する。また旧コードの削除にあたっては、「未 verify なら requeue」（cleanup へ到達させない）に相当するガードが各ロールでドメイン側・旧コード側のどちらかに必ず残ることを確認する（standalone・secondary の旧コードではこのガードは verify 呼び出しと同じ `if` ブロックにあるため、ブロックごと削除するとガードが失われる。<<risk-legacy>> 参照）。
* **テスト**: verify Job が無ければ作成 Operation を発行して requeue する、Job 実行中は何もせず後続へ継続する、成功／失敗に応じた condition 設定と後続への継続、未verify の間は cleanup に到達しない、各 Operation の発行内容。

== リスク・注意点

[#risk-persist-order]
=== status 永続化と Ceph 操作の順序不変条件

`provisionRBDSnapshot` は「PVC/PV マニフェストを status に**永続化した後に** RBD スナップショットを作成する」ことでクラッシュ時の孤児スナップショットを防いでいる（MB-C 内コメント参照）。「変更をメモリ上に溜めて `Run` の最後に一括永続化」する標準パターンではこの不変条件が壊れる。同種の不変条件として「ラベル（local-backup-target-pvc-uid）・finalizer を永続化した後にスナップショットを作成する」もある（`labelClusterID` 定数のコメントおよび `reconcileLocalBackup` のラベル付与コメント参照）。PR 7 の通り、リコンサイルを 2 周（ラベル・finalizer・マニフェストの永続化 → 次周でスナップショット作成）に分けることで、これらの不変条件を保ちながらドメイン化する。リコンサイルが 1 周増えるが、外部から見た状態遷移の順序は変わらない。同様に「途中で永続化してから次の外部操作を行う」箇所が他にないか、各 PR で移行対象コードを精査すること。

[#risk-finalize-order]
=== クリーンアップ・ファイナライズにおける外部作用と対象の永続化の順序

<<risk-persist-order>> とは逆向きの順序不変条件として、`primaryCleanup`・`secondaryCleanup`・`finalizeStandalone`・`finalizeSecondary` は「**他リソースへの外部作用を完了してから**、対象 backup 自身の変更を永続化する」順序に依存している。具体的には：

* source backup の diff-to アノテーション削除は、対象 backup の diff-from アノテーション削除（の永続化）より前に行われる。逆順にすると、間でクラッシュや Operation の失敗が起きた場合に diff-from が先に消え、以降のリコンサイルは source を特定できなくなる。source には diff-to が残り続け、`finalize*` は diff-to があると何もしないため、source の finalize が永久にブロックされる。
* finalizer の除去は、Job・PVC・PV と RBD スナップショットの削除がすべて完了した後に永続化される。逆順にすると、finalizer 除去の永続化と同時に MantleBackup が消滅するため、その後の削除 Operation が失敗・クラッシュした場合にリソースがオーファン化し、それを再試行するリコンサイルも存在しなくなる。

一方、ユースケース層の `Run` の標準的な順序は「対象の永続化 → Operations の適用」であり（new-architecture.adoc）、素朴に 1 パスでドメイン化するとこの順序が逆転する。そこで cleanup・finalize は次のように**複数パスに分解**する：

* 削除対象（source の diff-to アノテーション、cleanup 対象の Job・PVC・PV）が事前取得データ上に残っている間は、削除 Operation を発行して requeue し、対象 backup 自身は変更しない。
* それらがすべて消えたことを確認できたパスで、対象 backup 自身の変更（diff-from・sync-mode アノテーションの削除。finalize では加えて RBD スナップショット削除（interface・同期実行）・メトリクス削除・finalizer 除去）を行う。このパスでは、対象の変更より先に完了していなければならない Operation を発行しない。

これにより `Run` の標準順序（永続化 → Operations）のままで現行の順序不変条件を保てる。ただしオブジェクトストレージ上のエクスポートデータ削除と中間スナップショット削除の完了確認は行わない（前者の確認は S3 への読み取りを増やすため。いずれも対象 backup の変更との順序依存がなく再実行可能であり、現行も cleanup のたびに発行している）。K8s リソースの削除がキャッシュへ反映されるのを待つ分、cleanup・finalize のリコンサイルが現行の 1 パスから複数パスに増える（<<risk-requeue>> の許容例外）。

=== 結果に依存する外部呼び出しとロック保持

`createRBDSnapshot`（作成結果を同一パス内で status へ反映）、`lockVolume`/`unlockVolume`（複数リコンサイルパスにわたるロック保持）などは Operation では表現できない。これらは無理に Operation 化せず、ドメイン層定義の narrow interface で扱う（<<d3>>）。Operation 化と interface 化の判断に迷ったら「呼び出し結果がその場の判定・出力に使われるか、またはリコンサイルパスをまたいで保持すべき状態か」を基準にする。

[#risk-op-order]
=== Operation 実行の順序と失敗時の打ち切り

PoC の `infra.KubernetesClient.ApplyReconcilerOperations` は、Operation が失敗しても `errors.Join` で後続の実行を続ける。一方 MB には「diff-to アノテーションの付与 → `SetSynchronizing` → export Job 作成」のように、先行の失敗時に後続を実行してはならない順序依存の Operation 列がある。MB 用の Operation 適用は「発行順に実行し、失敗したら残りを打ち切る」契約とし、最初に Operation 実行器を導入する PR 6 で定める。その際 MBC 側の既存挙動を変えないこと（実行器を分けるか、MBC も打ち切りセマンティクスへ統一して問題ないかは PR 6 で判断する）。

なおこの打ち切り契約は、new-architecture.adoc の「渡されたイベントが複数ある場合、エラーの有無に関わらず全てのイベントの実行を試行する」という記述からの**意図的な逸脱**である。PR 6 で契約を定める際、new-architecture.adoc 側にも「順序依存の Operation 列を持つリコンサイラでは失敗時の打ち切りを許容する」旨の例外を追記する。

=== 事前取得によるアクセス増加

読み取りをユースケース層の事前取得に変えると、従来は条件付きだった K8s/gRPC/S3 アクセスが毎回発生しうる。K8s の読み取りはキャッシュ経由のため増加は許容するが、**gRPC・S3・`rbd` コマンドの呼び出し回数は増やさない**こと。取得の要否は、従来と同じ条件を実装したドメイン層の判定関数（純粋関数）をユースケース層から呼び出して決める。判定条件そのものをユースケース層に書いてはならない（ドメインロジックの漏出を防ぎ、判定にユニットテストを書けるようにするため。<<d3>> 参照）。

[#risk-legacy]
=== legacy 委譲境界のリスク

移行期間中は「どの状況をドメイン層が処理し、どの状況を旧コードに委譲するか」の境界が PR ごとに動く。委譲を判定する `if` 条件が削除した旧コードの分岐条件と一致していないと、特定の状況がどちらの経路でも処理されない（または二重に処理される）恐れがある。サブフロー移行 PR のレビューでは、追記した `if` 条件・legacy 委譲条件・削除した旧コードの分岐条件の対応を必ず突き合わせる。ロール完成 PR（PR 10・14・17）はロジック変更を含まない削除主体の PR とし、既存のインテグレーション・E2E テストの通過をもって等価性を確認する。

[#risk-requeue]
=== requeue タイミングの等価性

旧コードの `reconcile.Requeue()` は `REQUEUE_RECONCILIATION_AFTER` 環境変数由来の遅延を持つ。ドメイン化の際に requeue の発生箇所・回数が変わると、バックアップ完了までの時間が観測可能に変わりうる。原則として旧コードと同じ箇所で同じ種別の結果を返すこと。ただし次の例外は許容する：

* PR 7：`provisionRBDSnapshot` の 2 周分解により、スナップショット作成までのリコンサイルが 1 周増える。また、逐次 `if` の「処理を実行したら return する」構造により、従来 1 パス内で連続実行されていたサブフローの境界（スナップショット作成 → verify 開始など）でもそれぞれ 1 周増える。
* PR 8：verify リソース作成の `if` が return するため、検証開始パスでリコンサイルが 1 周増える（現行は作成と同一パスでレプリケーションも進行する。<<d7>> 参照）。
* PR 9・16：cleanup・finalize の複数パス分解（<<risk-finalize-order>>）により、アノテーション削除・finalizer 除去が削除完了の確認後のパスへ移り、リコンサイルが数周増える。
* PR 11・13：マニフェスト同期の 2 周分解により、初回同期のリコンサイルが 1 周増える。また「セカンダリに対象 backup が見つからない」場合に Failed としていた経路が正常な requeue に変わり、同期中のマニフェスト再送信が初回のみになる（PR 11 参照）。
* 現行は verify 完了後に余分なリコンサイルが 1 周発生している。原因はロールにより異なる：primary では `updateMantleBackupCondition` が DeepCopy に対する `Patch` を行うためメモリ上の backup に結果が反映されず、後続の判定が古い condition を見て requeue する。standalone・secondary では verify 呼び出し後に無条件で requeue を返すコードになっており、`Patch` の反映有無とは無関係に発生する。メモリ上で変更する標準パターンと <<d7>> の構造への移行により、いずれの余分な 1 周も消える（requeue が減る方向の変化）。後者の解消は `Patch` 問題の副産物ではなく「無条件 requeue の削除」という意図的な変更であることに注意する。PR 8・10・14・17 の等価性確認ではこの差を織り込む。

=== 定数移動のワイヤ契約

PR 2 で移動する定数は primary↔secondary 間の通信・リソース契約であり、**値の変更は一切禁止**。移動時は文字列リテラルの diff がないことをレビューで確認する。
